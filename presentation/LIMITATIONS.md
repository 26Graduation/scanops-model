# 한계와 예상 반박 — 답 12개

> 규칙: **측정한 것만.** 각 답에 근거 파일과 수치를 붙인다.
> 여기 없는 질문에는 "재지 않았다"고 답한다.

### Q1. PrimeVul·CleanVul 같은 표준 벤치에서 왜 이기지 못했나?

**못 이겼다. 그 표에는 지는 숫자가 그대로 있다.**
AUC 는 CleanVul_v2 **0.6165**, PrimeVul **0.5618** 이다(`FINAL_ARCHITECTURE_REPORT.md` §3-4).
F1 은 두 벤치 모두 **자명 기준선 0.6667 을 어떤 운영점에서도 넘지 못한다.**

원인은 특정했다. **쌍 안의 두 판본이 얼마나 비슷한가**가 축이다:
유사도 0.00–0.30 구간에서 순위 정확도 **0.8379**, 0.95 이상 구간에서 **0.4770(우연 아래)**.
두 벤치는 전부 "같은 함수의 패치 전후"(유사도 중앙값 0.924 / 0.979)다.

### Q2. 쌍의 38% 가 슬라이스까지 동일하다면, 애초에 풀 수 있는 문제인가?

그 38% 는 **Joern 슬라이스** 기준이고(`JOERN_HYBRID_REPORT_V4.md` §4), 원본 파일 기준이 아니다.
원본에서는 **변경 줄이 0인 쌍이 하나도 없다** — 중앙값 2~3줄이 라벨을 가른다
(`DIFF_AWARE_RESULTS.md` §3-1). 즉 **정보는 입력에 있고, 우리가 안 보여줬던 것**이다.
그래서 `[DIFF]` 마커가 0.4600 → 0.6050 을 만든다.

### Q3. 전부 50:50 균형셋 아닌가?

**맞다. 전부 50:50 가정이다.** 실제 PR 트래픽의 유병률은 그보다 훨씬 낮다.
유병률이 낮으면 **같은 (recall, FPR) 에서 precision 은 더 떨어진다.**
이 보정은 **아직 재지 않았다**(`FINAL_ARCHITECTURE_REPORT.md` §8-2-3 규칙 4).

### Q4. 외부 모델이 이 데이터를 사전학습에서 봤을 수 있지 않나?

**그럴 수 있고, 그 방향은 외부에 유리하다.**
- 내부 test 는 CVEfixes 시간분할이라 공개 CVE 패치다.
- **레포 벤치 3종은 공개 취약 앱**(juice-shop 등)이라 외부가 봤을 가능성이 특히 크다.
누수 검사는 **학습셋 대비**로만 했고(유사도 ≥0.95: 내부 0.00% / CleanVul 0.00% / PrimeVul 1.04%,
`DIFF_AWARE_RESULTS.md` §3-3), **외부 모델의 사전학습은 우리가 검사할 수 없다.**

### Q5. Claude 에게 불리한 프롬프트를 준 것 아닌가?

두 조건으로 잰다.
- **PARITY**: 우리와 **바이트 동일한** 프롬프트·파서·12,000자 절단(사양 §2-b).
- **STRONG**: 시니어 AppSec CoT 를 허용하고 사고 예산을 10배로 준 조건(§2-d).

**맞출 수 없는 조건도 그대로 적는다**: Claude 5 계열은 `temperature` 를 받지 않는다(400).
따라서 **temp 0 은 우리 쪽에만 적용된다.** "동일 조건"이라고 쓰지 않는다.
STRONG 을 예산 안에서 돌리지 못했다면 그 칸은 **"미측정"** 이다.

### Q6. 함수 단위 벤치에서 그래프 기여가 0이었다면서, 왜 아직도 그래프를 파는가?

**파는 방식이 바뀌었다.** ABLATION 에서 ΔF1 **−0.0014**(CI 0 포함), unknown **91.6%** 였다
(`ABLATION_RESULTS.md`). 그래서 **판정에서 뺐고**, 남긴 것은 두 가지다:
① `vuln` 만 결과에 **추가**(safe/unknown 은 어떤 판정도 덮지 않는다 — graph safe 의 42.5% 가 오판),
② **evidence 표시**.
오늘 레포 벤치에서 그래프가 무엇을 더했는지는 **S2 − S1** 칸에 그대로 적혀 있다.

### Q7. `PRECISION-UNREACHABLE` 이 정확히 무슨 뜻인가?

**커브 전체에 도달점이 없다**는 뜻이다. CleanVul_v2·PrimeVul 에서
`precision ≥ 0.70 AND recall ≥ 0.10` 을 만족하는 임계값이 **0개**다
(`OPPOINT_RESULTS.md` §1-1b). 임계값을 옮겨서 해결되는 문제가 아니다.

### Q8. 사업계획서에 "7B" 라고 썼는데 지금은 9B 아닌가?

**계획서가 낡았다.** 현재 프로덕션은 **Qwen3.5-9B QLoRA**(`adapter_v1_fix.gguf`)다.
계획서의 "Qwen2.5-Coder-7B" 문장은 정정 대상이다(`BUSINESS_PLAN_EDITS.md`).

### Q9. 원가는 얼마인가?

**실측하지 않았다.** GPU 사양은 Linux+CUDA 환경이 없어 미실측이고
(`FINAL_ARCHITECTURE_REPORT.md` §9), 오늘도 RunPod 가용 GPU 가 0이라 GPU 원가를 못 쟀다.
있는 것은 **macOS M3 로컬 실측**(CPU 19.3s/88.3s, RAM 피크 5.58GiB)뿐이다.
**"월 얼마"를 말하려면 GPU 시간당 단가 × 실측 처리량이 필요하고, 그 실측이 없다.**

### Q10. Joern taint 의 상한은 어디인가?

전건 1,878건에서 precision **0.5068**, CI **[0.4715, 0.5434]** — **CI 상한이 0.60 에 미달**이라
사전등록 기준(`SIGNAL` = 점추정 ≥0.60)에서 통계적으로 배제됐다(`JOERN-NO-BETTER`).
OWASP taint 전용 110건에서도 precision **0.5172**, FPR **0.7636**.
홀드아웃 56건에서 FPR 0.6429 로 내려갔지만 사전등록 기준 0.50 미달 → **`NOT-IMPROVED`**.

### Q11. `[DIFF]` 마커는 게이트를 통과했나?

**통과하지 못했다.** 판정은 **`CB-PARTIAL`** 이고, 막은 것은 **동점률 0.155 > 0.10** 하나다
(`DIFF_AWARE_RESULTS.md` §6-4). 그런데도 제품에 붙인 이유는 세 가지다:
① 위치 상쇄 후 개선의 **CI 하한이 +0.065 > 0**, ② **단건 회귀 없음**(내부 test 0.9101 동일,
CyberNative +0.0176), ③ **안전 판본 오탐률 0.065 불변**.
**게이트 통과가 아니라 제품 판단**이고, 되돌림은 `SCANOPS_PR_DIFF_MARKER=0` 하나다.
이식 회귀 4종은 전부 통과했다(`rebuild/out/diff_marker_port_check.json`).

### Q12. 레포 벤치 정답표를 너희가 만들었는데 믿을 수 있나?

**정답표의 좌표는 우리가 고르지 않았다.** juice-shop 소스 안의
`// vuln-code-snippet vuln-line <challengeKey>` 마커를 그대로 읽었다 —
레포 자신이 코딩 챌린지 정답 판정에 쓰는 값이다(`lib/codingChallenges.ts:76` 이 같은 정규식을 쓴다).
44건 전부 파일:라인이 붙는다 → confidence **high**.

**우리가 붙인 것은 `cross_file` 뿐이고, 그건 confidence `med` 로 낮춰 적었다.**
규칙을 문서에 적고(source→sink 가 2개 파일에 걸치거나, 판정 근거가 다른 파일에 있음 + 그 파일을 지목),
**어떤 스캔 결과도 보기 전에** 커밋했다(커밋 `72d18e0` → 스캔은 그 이후).

**표본은 부족하다.** 스캔 범위(TypeScript) 안에 든 정답은 **33건**으로
사전등록 최소치 **40건에 미달**한다. cross_file 은 16건으로 최소치 12건을 넘는다.
→ 사양 §6-b 대로 **"표본 부족"** 으로 적고, GRAPH 판정은 **참고값**으로만 싣는다.

### Q13(추가). 레포 벤치의 "오탐"은 진짜 오탐인가?

**아니다. 상한이다.** 정답표는 juice-shop 챌린지 중 **라인 마커가 있는 것만** 담는다(9개 파일).
juice-shop 은 의도적으로 취약한 앱이고 마커 없는 취약점이 훨씬 많다 →
**여기서 오탐으로 센 것 중 상당수가 실제 취약점일 수 있다.**
그래서 **오탐 수는 상한, precision 은 하한**으로만 읽는다.
해석 가능한 것은 (a) 같은 정답표로 잰 **recall**, (b) 같은 파일 집합에서의 **arm 간 상대 경보율**뿐이다.

### Q14(추가). 매칭을 파일 단위로 한 것은 너무 후한 것 아닌가?

**후하다. 그리고 세 arm 에 똑같이 후하다.**
우리 모델도 Claude 도 **라인 번호를 출력하지 않는다**(4줄 서식에 없고, 제품 `/analyze/batch` 도
파일 단위 판정만 낸다). 라인 기준을 유지하면 LLM arm 두 개가 구조적으로 0이 되어 비교가 성립하지 않는다.
이 변경은 **어떤 스캔도 돌리기 전에** 사양 §11 에 기록했다.
Joern·graph 는 라인을 갖고 있어서 `sink_line ±10` 적중 여부를 **부가 정보로만** 남겼다.

### Q15(추가). Joern 이 프로젝트 CPG 를 만들 때 OOM 폴백을 썼나?

**쓰지 않았다.** juice-shop 257 파일 프로젝트 CPG 를 **149초, `-Xmx 4g`, 타임아웃 없이** 빌드했다
(`rebuild/out/repo_bench_juice-shop_joern.json`). 사전등록한 부분 그래프 폴백은 **발동하지 않았다.**
`-Xmx` 를 사양의 "가용 RAM 60%" 대신 4g 로 낮춘 이유는 같은 기계에서 llama-server 가
동시에 돌고 있었기 때문이고, 그 사실과 값을 기록했다.
