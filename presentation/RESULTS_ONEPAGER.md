> ### ⚠ 이 표를 읽기 전에 — **이 벤치는 포화됐다**
> 
> **세 arm 의 recall 이 전부 1.0000 로 같다. 즉 recall 은 arm 을 가르지 못한다.**
> 정답이 있는 파일이 9개뿐인데 세 arm 모두 전체 파일의 45~62% 를 vuln 으로 판정한다. 파일 단위 매칭에서는 그 9개가 자동으로 전부 포함된다 → recall 이 1.0 으로 붙는다. **사전등록한 설계의 결함이고, 결과를 본 뒤 지표를 바꾸지 않는다.** 대신 이 벤치가 실제로 가르는 것만 읽는다: (a) **arm 간 경보율**, (b) **S2 − S1 = 그래프가 새로 잡은 정답 수와 추가로 켠 경보 수**, (c) 카테고리까지 맞힌 비율(recall_cat).
> 
> **사전등록한 설계의 결함이다.** 결과를 본 뒤 지표를 바꾸지 않았고, 대신 이 벤치가
> 실제로 가르는 것만 아래에서 읽는다.

**사전등록 판정 = `GRAPH-TIE`** (구속력: **없음 — 표본 부족**)

- S2 − C1 cross-file recall 차 = **+0.0000** (WIN 기준선 +0.20, CI 겹침 True)
- **그래프 순기여 S2 − S1** — 이 벤치가 실제로 가르는 값:
  - 새로 잡은 정답 파일 **0개** (없음)
  - 추가로 켠 경보 **27개 파일** (경보율 0.4475 → 0.5525)
  - → **이 레포에서 그래프는 탐지를 더하지 않고 경보만 더했다.**
- 발표 문구(사전 고정) → **"보조 탐지 + 근거 표시"**

**그래프 3성분이 각각 무엇을 냈나**

| 성분 | vuln 판정 파일 | 시간 | 비고 |
|---|---|---|---|
| 자체 `code_graph` (멀티파일 JS/TS) | **0** | 0.07s | sink 패턴 5개(React/DOM XSS 3 + fetch/axios SSRF 2)뿐 — Express·sequelize·Angular 경로에 발화하지 않는다 |
| `multi_graph` (단일파일 다언어) | 15 | 0.21s | unknown 이 대부분(ABLATION 91.6% 와 같은 성질) |
| **Joern v4 프로젝트 CPG** | 73 | 149.0s | 257파일 1개 CPG, `-Xmx 4g`, 타임아웃 없음. findings 3660건 중 sanitized 2323 |

> **precision 과 오탐 수를 절대값으로 읽지 말 것.** 정답표는 juice-shop 챌린지 중 소스에 `vuln-code-snippet vuln-line` 마커가 있는 것만 담는다(9개 파일). juice-shop 은 의도적으로 취약한 앱이고 마커 없는 취약점이 더 많다 → 여기서 '오탐'으로 센 것 중 상당수가 실제 취약점일 수 있다. 따라서 **오탐 수는 상한, precision 은 하한**이다. 해석 가능한 것은 (a) 같은 정답표로 잰 **recall**, (b) 같은 파일 집합에서의 **arm 간 상대적 경보율(flag_rate)** 뿐이다.

## 각주 (표를 인용할 때 함께 붙인다)

1. **누수 방향은 외부에 유리하다.** 내부 test 는 공개 CVE 패치(CVEfixes 시간분할)이고,
   레포 벤치는 공개 취약 앱(juice-shop)이다 — 외부 모델이 사전학습에서 봤을 가능성이 크다.
   우리는 **학습셋 대비 누수**만 검사했다(유사도 ≥0.95: 내부 0.00% / CleanVul 0.00% / PrimeVul 1.04%).
2. **전부 50:50 균형셋 가정이다.** 실제 PR 유병률은 더 낮고, 낮으면 precision 은 더 떨어진다. 이 보정은 재지 않았다.
3. **레포 벤치 매칭은 파일 단위다.** 두 LLM arm 모두 라인 번호를 출력하지 않기 때문이고, 세 arm 에 똑같이 적용했다.
   → recall 이 낙관적이 된다.
4. **레포 벤치 precision 은 하한, 오탐 수는 상한이다.** 정답표는 라인 마커가 있는 챌린지만 담는다.
5. **Claude 에 레포 전체를 주는 arm 은 만들지 않았다** — 컨텍스트·비용상 제품 사용 방식이 아니다.
