## §2 목표 — **사용자가 원래 목표를 유지하기로 결정했다**

**MUST: 외부 벤치 AUC ≥ 0.75** (`V3_RESULTS.md` §10 이 제시한 목표선).

> **이 목표는 오늘 측정이 미달을 예측한 상태에서 유지된 것이다.**

>
> 사용자에게 이 근거를 제시했고, **원래 목표로 그대로 돌린다**는 결정을 받았다(2026-08-17).
> 따라서 이 실행은 **목표 달성 시도인 동시에 DOSE 외삽의 검정**이 된다.
> 미달하더라도 §8 규칙대로 **정직하게 미달로 보고한다.**

### 미리 인정하는 교란 (중요)

**이 실행은 두 가지를 동시에 바꾼다 — 학습량(+120%)과 학습률(2e-4→1e-4).**
따라서 결과가 좋든 나쁘든 **어느 쪽 덕/탓인지 이 실행 하나로는 분리할 수 없다.**
#4 가 원래 두 요소를 묶어 제안했으므로 그대로 실행하되, **이 한계를 결과 보고에 명시한다.**

### epoch 수 선택

#4 는 "2~3 epoch"라고 했다. **2 epoch(1,674 step)를 택한다.**
근거: 3 epoch 는 학습만 ~6.6h 라 §6 예산 상한을 넘긴다. 2 epoch 는 **원래 계획했던 학습량 그대로**이므로
"완주"라는 #4 의 취지를 만족한다. 이 선택을 결과 보고에 적는다.

### 부가 판정 (게이트와 별개, 미리 등록)

1. **DOSE 외삽 검정**: 관측 AUC 를 DOSE 예측(PrimeVul 0.6286 / CleanVul 0.6793)과 대조한다.
   - 관측 < 예측 → 감속이 확인됨 (선형 외삽이 낙관적이었다)
   - 관측 > 예측 → 학습량만으로 설명 안 되는 이득 (lr 변경 기여 가능성 — 단 §3 교란 때문에 단정 불가)
2. **v1 대비 공정 비교**: §9-1 이 인정한 "학습 예산이 달라 v1 vs v3 비교는 불공정하다"는 교란이
   이 실행으로 해소된다. **AUC 기준으로** v1 대비 우열을 적는다(부록 A 실무결론 1: 비교는 AUC 로).
3. **진동 재확인**: GEN-F1 을 매 150 step 기록한다. lr 1e-4 에서 step 600 급락(0.406)이 재현되는지 본다.
   재현되지 않으면 lr 이 원인이었다는 **정황**이 된다(단정하지 않는다 — 시드 1개).

## §10 사전등록 추가 — 중간 게이트와 채택 규칙 (2026-08-17, **결과 보기 전 추가**)

> 이 절은 학습 결과·채점 결과를 **하나도 보기 전에** 작성·커밋됐다.
> 추가 이유: 오늘 `DOSE-RESPONSE-WEAK`(`b1b8817`)가 **0.75 미달을 예측**했다.
> 그럼에도 #4 를 실행하기로 했으므로(§2), **헛돈을 막는 중간 정지선**과
> **0.75 미달일 때 무엇을 근거로 채택/기각할지**를 미리 박아둔다.
> §4 의 원래 게이트(PASS/PARTIAL/FAIL)는 **그대로 유효**하다. 이 절은 그 위에 얹는다.

### §10-1 MID-GATE — 완주 전 정지선

| 항목 | 값 |
|---|---|
| 시점 | **step ≈ 800**, 첫 체크포인트가 디스크에 저장된 직후 |
| 측정 | pod 안에서 `score_logprob.py <ckpt> v4mid cleanvul_v2_tune` (676건, 수 분) |
| 비교 대상 | **v3s42 @ step750 의 CleanVul_v2 tune AUC = `0.6381`** (오늘 재현 확인) |
| **STOP** | ΔAUC 점추정 **≤ 0** → **즉시 pod terminate**, 판정 `MID-GATE-STOP` 기록, GPU 트랙 종료 |
| **GO** | ΔAUC 점추정 **> 0** → 1,674 step 완주 |

- **CI 를 쓰지 않고 점추정을 쓰는 이유**: 676건의 CI 는 넓다. CI 하한을 요구하면 거의 항상 STOP 이 되고,
  CI 상한을 요구하면 거의 항상 GO 가 된다. 중간 게이트의 목적은 **판정이 아니라 예산 방어**이므로
  "적어도 방향은 맞는가"만 묻는다. **MID-GATE 통과는 성능 주장이 아니다.**
- tune split 을 쓰는 이유: report 를 중간에 들여다보면 이후 판정이 오염된다.

### §10-2 최종 판정 (§4 게이트에 추가)

| 판정 | 조건 |
|---|---|
| **TARGET-MET** | CleanVul_v2 **report AUC ≥ 0.75** (= §2 의 원래 목표. **미달로 예상하고 있다**) |
| **ADOPT** | 아래 **셋 모두** 성립 → 0.75 미달이어도 v4 를 배포 어댑터로 채택<br>① 내부 test ΔAUC **CI 하한 > 0**<br>② CleanVul_v2 report ΔAUC **CI 하한 > 0**<br>③ PrimeVul report ΔAUC **점추정 ≥ 0**<br>세 조건 모두 **기준선 v3s42@750 과 v1 둘 다에 대해** 성립해야 한다 |
| **NO-ADOPT** | 그 외 → **v1 유지** |

기준선 숫자(오늘 재현 확인, 이 표도 결과 전 고정):

| split | v1 | v3s42 @750 |
|---|---|---|
| 내부 test | 0.9052 | 0.8875 |
| CleanVul_v2 report | 0.6165 | 0.6208 |
| CleanVul_v2 tune | 0.6230 | 0.6381 |
| PrimeVul report | 0.5618 | 0.5802 |

- ΔAUC CI 는 **쌍 부트스트랩 2,000회**(같은 아이템 재표집, `bootstrap_ci.py` 관례).
- **v1 대비 내부 test 조건이 가장 빡빡하다** — v3s42 는 이미 v1 보다 내부 test 가 낮다(0.8875 < 0.9052).
  v4 가 v1 의 0.9052 를 CI 하한 기준으로 넘지 못하면 ADOPT 되지 않는다. 이 어려움을 알고 박는다.

### §10-3 이 추가가 바꾸지 않는 것

- §2 의 목표선 0.75 를 낮추지 않는다. ADOPT 는 **목표 달성과 다른 이름**이며, 보고서에서 절대 혼용하지 않는다.
- §8(미달 보고 규칙)은 그대로다.
