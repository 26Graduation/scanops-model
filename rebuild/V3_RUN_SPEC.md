## 0. 너의 역할

너는 이 작업을 **6시간 동안 무인으로 자율 실행**한다. 사용자는 자고 있거나 자리에 없다.

- 중간에 사용자 확인을 기다리지 마라. 판단이 필요하면 **가장 합리적인 선택을 하고 이유를 로그에 남겨라**.
- 막히면 우회하라. 한 접근이 30분 이상 진전이 없으면 접고 다른 걸 시도하고, 접은 이유를 기록하라.
- **30분마다** `rebuild/out/v3_progress.md`에 진행 상황을 append하라. 사용자가 아침에 이 파일만 읽어도 상황을 파악할 수 있어야 한다.
- 목표를 달성하면 거기서 멈추지 말고, 남은 시간으로 **재현성 검증(다른 시드)과 마진 확대**를 하라.

### 전략적 관찰 (이걸 이용해라)

- **Claude의 약점은 오탐이다.** 외부 벤치에서 FPR 0.80. 재현율은 0.84로 높지만 정밀도가 0.51이라 F1이 0.63에서 막힌다.
- **우리 약점은 재현율이다.** PrimeVul FPR 0.106으로 매우 보수적인데 재현율이 0.128. 즉 **모델이 지나치게 SAFE 쪽으로 치우쳐 있다.**
- 따라서 승부처는 **"FPR을 0.2~0.3까지 허용하면서 재현율을 0.6 이상으로 끌어올리는 것"** 이다. 그러면 F1 0.65~0.75가 나오고 Claude를 넘는다.
- 이건 **운영점(operating point) 문제**이지 순수 모델 능력 문제가 아닐 가능성이 크다. §6의 (A)(D)를 최우선으로 시도하라.

## 2. 확정된 사실 (재조사하지 말고 그대로 사용)

### v2가 실패한 원인 — 이미 규명 완료

`rebuild/build_dataset_v2.py:211`:

```python
groups[s["meta"].get("pair_id") or s["meta"]["cve_id"]].append(s)
```

CleanVul 행은 `cve_id=''`, `pair_id=None`이다. 따라서 **3,617건이 `''`라는 단일 그룹 키로 붕괴했고, 그 덩어리가 통째로 val로 빠졌다.**

결과:
- `val_v2` = safe 4,552 / vuln 726 → **86%가 safe** (v1 val은 safe 665 / vuln 518로 균형)
- `train_v2`에 편입된 CleanVul은 502건뿐 (설계 의도인 70%가 아님)
- `train_qlora.py`의 `metric_for_best_model="eval_loss"` → **"항상 SAFE"가 val loss 최적해**
- → v2 모델이 전부 SAFE를 뱉음 (PrimeVul recall 0.000)

**이 진단이 맞는지 v3에서 검증하고, 결과를 최종 리포트에 명시하라.**

### 재실행하지 말 것 (비용 낭비)

- Claude / Grok 비교 채점은 이미 `out/compare_*_report.json`에 있다. **ANTHROPIC_API_KEY / XAI_API_KEY로 재실행 금지.** 위 표의 숫자를 그대로 baseline으로 써라.
- 단, 우리 모델의 출력 포맷이나 `bench_common.py` 파서를 바꾸면 공정 비교가 깨진다. §3 참조.

## 3. 반드시 지킬 것 (연구 무결성 — 위반 시 결과 전체가 무효)

1. **평가 데이터 절대 수정 금지**: `data/test.jsonl`, `data/primevul_test.jsonl`, `data/cleanvul_v2_test.jsonl`. 읽기만 하라.
2. **학습 데이터는 위 3종과 dedup**: `(cve_id, 공백정규화 소문자 코드 SHA1)` 기준. build_dataset_v2.py의 dedup 로직을 재사용하라.
3. **채점은 `rebuild/bench_common.py`를 그대로 사용**. 파서·지표 정의를 바꾸지 마라. 정말 바꿔야 한다면 v1과 Claude 예측 파일도 같은 파서로 재채점해서 표를 통째로 다시 만들어라(예측 파일은 이미 `out/`에 있으니 API 비용은 안 든다).
4. **운영점 튜닝을 test에서 하지 마라.** 투표 임계값·logprob 임계값·앙상블 가중치는 반드시 별도 split에서 정하라:
   - 각 외부 test에서 **층화 20%를 `tune` split**으로 떼어라(시드 42 고정, 쌍은 쌍째로 이동).
   - 튜닝은 `tune`에서, **최종 보고 숫자는 나머지 80%의 `report` split**에서.
   - 리포트에는 tune/report 두 숫자를 **모두** 적어라. 격차가 크면 과적합 신호다.
   - 내부 test는 손대지 말고 통째로 report용. 운영점은 `val`에서 정하라.
5. **v1 산출물 보존**: `out/adapter/`를 덮어쓰지 마라. 새 산출물은 `out/v3_<실험명>/`.
6. **단일 시드 금지**: 최종 채택 후보는 **최소 2개 시드**로 재학습해 분산을 확인하라. 시드 간 F1 차이가 0.03 이상이면 리포트에 경고로 남겨라.
7. **체리피킹 금지**: 시도한 모든 실험을 결과가 나쁘더라도 전부 기록하라. "최고만 보고"는 금지.

## 4. 1단계 — 데이터 재구축 (필수, 먼저 하라)

`rebuild/build_dataset_v3.py`를 새로 작성하라. `build_dataset_v2.py`를 베이스로 하되 다음을 수정:

1. **그룹 키 붕괴 수정**:
   ```python
   key = s["meta"].get("pair_id") or s["meta"].get("cve_id") or f"orphan:{code_hash(code)}"
   ```
   빈 문자열·None이 하나로 뭉치지 않게 하라.
2. **val 층화**: 전체의 10%, 라벨 비율을 내부 test와 맞춰라(safe:vuln ≈ 54:46). 언어 분포도 가능한 한 맞춰라.
3. **CleanVul 시간분할 held-out(최신 30%)은 val에 넣지 마라.** 평가 전용으로 분리 보관.
4. **소스별 상한**: 한 소스가 train이나 val을 잠식하지 않도록. 특히 CleanVul은 safe-only라 라벨을 왜곡한다.
5. **통계 출력**: `out/v3_data_stats.json`에 `split × source × label × language` 교차표를 저장하고, `v3_progress.md`에도 요약을 남겨라. **이 표를 확인하기 전에 학습을 시작하지 마라.**

**게이트**: val의 safe 비율이 0.60을 넘거나 vuln이 0.35 미만이면 학습을 시작하지 말고 데이터 빌더를 고쳐라.

## 5. 2단계 — 학습

`rebuild/train_qlora_v3.py` (기존 `train_qlora.py` 기반):

- **베이스 모델**: `unsloth/Qwen3.5-9B` (기존과 동일)
- **체크포인트 선택 기준을 바꿔라**: `metric_for_best_model="eval_loss"` → **생성 기반 F1**. 매 eval step마다 val에서 층화 샘플 200~300건을 실제로 생성·채점(`bench_common.parse`/`score` 사용)해 F1을 계산하는 콜백을 구현하라. 이게 v2 실패의 두 번째 원인이었다.
  - 구현이 학습을 너무 느리게 만들면(> 20% 오버헤드), eval 주기를 늘리거나 샘플을 150건으로 줄여라. **eval_loss로 되돌아가지는 마라.**
- **A100 80GB에 맞게 상향**: `BATCH_PER_DEVICE`를 8~16으로 올리고 `GRAD_ACCUM`으로 유효 배치 16~32 유지. OOM 나면 절반씩 낮춰라. (기존 값 2×8은 24GB 기준이라 A100에서 낭비)
- **LoRA rank**: 16(기존)과 32를 비교하라.
- 시드는 42, 1337 두 개.

## 6. 3단계 — 추론 기법 (여기서 승부가 난다)

사용자가 명시적으로 요청했다: *"앙상블 이런거 써도 되고, 여러 에이전트 돌려도 되고, 모델 여러개를 지들끼리 싸우게 만들어서 좋은 답변 뽑는 기법"*.

**우선순위 순으로 시도하라. (A)와 (D)가 비용 대비 효과가 압도적이다.**

### (A) Self-consistency voting — 최우선

temperature 0.7로 **k=5 샘플** 생성 → "vulnerable" 표가 **t개 이상**이면 VULNERABLE.
`t`를 1~5로 스윕하면 ROC 곡선 전체가 나온다.

현재 PrimeVul recall 0.128 / FPR 0.106은 극단적으로 보수적이다. **t=1 또는 t=2에서 재현율이 급상승할 것으로 예상된다.** 이것만으로 목표를 달성할 가능성이 있다. **가장 먼저 하라.**

### (D) logprob 임계값 — (A)와 함께 또는 대신

첫 생성 토큰에서 `VULNERABLE` vs `NONE`의 logprob 차이를 연속 점수로 뽑아 임계값을 스윕하라.
(A)보다 훨씬 싸다(샘플 1회). 가능하면 이걸 우선하고 (A)로 보강하라.

### (B) 2단계 파이프라인 (high-recall detector → adjudicator)

`ScanOps_Final_Report_v5.md`의 아키텍처와 동일한 발상:
- Stage A: 재현율 높은 모델이 후보를 넓게 뽑음 (Qwen2.5-Coder-7B가 recall 0.919 / FPR 0.402로 이 역할에 맞음)
- Stage B: 정밀한 모델이 후보를 걸러냄 (Qwen3.5-9B v3)

두 모델을 다 학습해야 하므로 시간이 든다. (A)(D)로 목표 미달일 때 시도하라.

### (C) 앙상블 / 모델 간 토론 (debate)

서로 다른 시드·rank·데이터 조합의 어댑터 2~3개를 만들어:
- **다수결**: 단순하고 안정적
- **debate**: 판정이 갈린 케이스만 각 모델에게 상대 의견을 보여주고 재판정시킨 뒤 최종 표결

**주의**: debate는 구현·디버깅 비용이 크고 이득이 다수결 대비 작은 경우가 많다. (A)(B)(D)를 다 하고 시간이 남을 때만 하라. 하게 되면 "판정이 갈린 케이스"에만 적용해 비용을 줄여라.

### 모든 기법에 공통으로 요구되는 것

각 기법의 **추론 비용을 반드시 함께 보고하라**: 케이스당 샘플 수, 평균 지연(초), 상대 비용 배수.
프로덕션은 실시간 PR 스캔이라 k=5는 5배 느리다. **F1이 0.02 오르는 대가로 5배 느려지는 건 나쁜 거래다.** 리포트에 성능-비용 파레토 표를 넣어라.

## 7. RunPod 운영

- `RUNPOD_API_KEY`가 `scanops-model/.env`에 있다. **A100 80GB** 사용.
- **최대 동시 2 pod**까지 허용(병렬 실험용). 그 이상은 안 된다.
- **총 예산 상한 $18** (계정 잔액 $21, 여유분 $3 남김). 누적 비용을 추적하고, **$14를 넘으면 새 pod 기동 금지**, 진행 중인 것만 마무리하라. $18 도달 시 전부 종료하고 보고하라.
- 잔액이 바닥나면 pod이 강제 종료되어 산출물을 잃는다 — **중간 산출물(체크포인트·predictions)을 30분마다 로컬로 회수**하는 이유가 이것이다.
- **작업이 끝나면 반드시 모든 pod을 종료하라.** 실행 시작 시점부터 **6시간 30분 후 무조건 전체 종료**하는 안전장치를 걸어라. 이게 제일 중요하다 — 켜둔 채로 끝나면 돈이 계속 나간다.
- **데드맨 스위치 (필수)**: 너 자신(오케스트레이터)이 토큰 한도·크래시로 중간에 죽을 수 있다고 가정하라. 따라서 pod 종료를 너에게 의존시키지 마라. **모든 pod의 시작 스크립트 첫 줄에 자기파괴 워치독을 심어라**:
  ```bash
  # pod 기동 직후 백그라운드로 — 6.5시간 뒤 무조건 자폭
  nohup bash -c 'sleep 23400; runpodctl remove pod $RUNPOD_POD_ID' >/dev/null 2>&1 &
  ```
  그리고 각 실행 스크립트(run_v3.sh 등)의 정상 종료 경로 마지막에도 `runpodctl remove pod $RUNPOD_POD_ID`를 넣어라. 작업이 일찍 끝나면 일찍 죽는다. **워치독이 심어졌는지 pod 기동 직후 `ps`로 확인하고 v3_progress.md에 기록하라.**
- **토큰 절약 (오케스트레이터 생존)**: 학습이 도는 동안 로그를 통째로 읽지 마라. 폴링은 10~15분 간격, `tail -n 20` 수준으로. 대용량 predictions/jsonl 파일을 컨텍스트로 읽지 말고 집계 스크립트를 pod에서 돌려 report.json 숫자만 가져와라.
- 네트워크 볼륨 `scanops-model_volume`이 있다. HF 캐시(`HF_HOME`)를 여기 두면 모델 재다운로드를 아낄 수 있다.
- pod의 학습·채점 로그와 산출물(어댑터, predictions, reports)을 **로컬 `rebuild/out/`으로 회수**한 뒤 종료하라. 어댑터가 크면 리포트와 predictions만이라도 반드시 회수하라.
- 기존 `run_v2.sh` / `run_qwen25coder7b.sh`가 pod 안에서의 실행 흐름 참고가 된다(`cd /workspace/rebuild`, `HF_HOME=/workspace/hf`, unsloth 설치 등).

## 9. 최종 산출물

`rebuild/out/V3_RESULTS.md` — **한국어로** 작성. 구성:

1. **한눈에 보는 표**: v1 / v2 / v3-최종 / Claude / Grok × (내부 test / PrimeVul / CleanVul) × (F1, recall, FPR, precision)
2. **목표 달성 체크리스트**: MUST 3개 + STRETCH 2개 각각 ✅/❌와 실제 수치
3. **실험 로그 전체**: 시도한 모든 실험(데이터 변형 × 하이퍼파라미터 × 추론 기법)과 각각의 결과. 실패한 것도 전부.
4. **v2 실패 원인 검증**: §2의 진단이 맞았는지, v3 데이터 통계와 대조해 결론
5. **성능-비용 파레토 표**: 각 추론 기법의 F1 대비 지연·샘플 수
6. **채택 권고**: 프로덕션에 무엇을 반영해야 하는지. GGUF 변환·`api_rebuild.py` 서빙 반영 절차 포함
7. **남은 한계**: 정직하게. 시드 분산, tune/report 격차, 미검증 항목
