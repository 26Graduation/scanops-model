# CTX-1 정성 확인 — 점수가 크게 움직인 케이스 (사양서 §6)

기준: `score(T1) − score(T0)` 의 절댓값 상위/하위. 전체 248건 기준
평균 이동 **−0.442**, 표준편차 0.590, 범위 [−3.000, +1.125].

---

## 0. 이 절의 결론 (먼저)

**문맥은 점수를 움직였지만, 쌍 안에서 취약본과 패치본을 **똑같이** 움직였다.**

| 측정 | 값 |
|---|---|
| 문맥이 취약본 점수를 움직인 폭 (평균) | **−0.447** |
| 문맥이 패치본 점수를 움직인 폭 (평균) | **−0.436** |
| 두 이동량의 상관계수 r | **0.846** |
| 평균 \|이동량\| | 0.550 |
| 평균 \|쌍 내부 이동량 차이\| | **0.198** |
| 이동량이 완전히 동일한 쌍 | 30 / 124 |

이동의 크기(0.550)에 비해 쌍 내부의 차이(0.198)가 작다.
**문맥은 판별 신호가 아니라 편향(bias) 항으로 들어왔다** — 모델을 전반적으로
"안전" 쪽으로 밀었을 뿐, 취약본과 패치본을 갈라내지 못했다.
이것이 §5 판정표에서 AUC는 그대로인데(0.5601 → 0.5571) argmax 재현율만
0.129 → 0.048로 붕괴한 이유다.

**상위 두 쌍이 쌍의 양쪽 모두 거의 같은 크기로 움직였다는 점에 주목하라.**
`pv_f5a038e68930_196801`은 −2.375 / −2.375로 **완전히 동일**하다.

### 판단을 가르는 정보가 실제로 들어 있었는가 — 없었다

`pv_9d2231c5d74e_207753` (리눅스 `copy_page_to_iter_pipe`)의 실제 취약/패치 차이는
**한 줄**이다:

```diff
  buf->ops = &page_cache_pipe_buf_ops;
+ buf->flags = 0;
  get_page(page);
```

`struct pipe_buffer`의 `flags` 필드가 초기화되지 않아 생기는 결함이다.
이걸 판정하려면 **`struct pipe_buffer`의 정의**와 **그 flags를 누가 읽는지**를 알아야 하는데,
둘 다 `lib/iov_iter.c` 안에 없다 (헤더 `linux/pipe_fs_i.h`에 있다).
우리가 넣어 준 문맥은 `#include` 목록, `__copy_page_to_iter()` 호출부, `sanity()` 본문이며
**셋 다 이 판단과 무관하다.** 그런데도 점수는 3.0이나 움직였다.

→ **정보가 아니라 길이·형식이 점수를 움직였다는 직접 증거.** T1-shuf가 T1과
같은 성능(AUC 0.5615 vs 0.5571)을 낸 것과 일관된다.

여기서도 1위 쌍은 +1.125 / +1.000으로 **양쪽이 같이** 움직였다.

### `pv_37da90248deb_202783` (php `Balloc`) — 문맥에 정보가 **있었는데도** 안 됐다

패치는 경계 검사와 NULL 검사를 추가한다:

```diff
  Bigint *rv;
+ if (k > Kmax) {
+     zend_error(E_ERROR, "Balloc() allocation exceeds list boundary");
+ }
...
  rv = (Bigint *)MALLOC(sizeof(Bigint) + (x-1)*sizeof(Long));
+ if (!rv) {
+     _THREAD_PRIVATE_MUTEX_UNLOCK(dtoa_mutex);
+     zend_error(E_ERROR, "Balloc() failed to allocate memory");
+ }
```

판단의 열쇠는 **`Kmax`가 무엇인가**인데, 이건 우리가 넣은 문맥 안에 실제로 있다
(파일 상단 매크로에 `Kmax` 정의 포함 — 기계 확인 완료).
그런데 이 쌍의 최종 판정은 여전히 갈리지 않았다. **정보를 줘도 쓰지 못한다.**

## 3. 기계 확인 — 문맥이 애초에 판단 정보를 담고 있었는가

"패치가 건드린 줄에 등장하는 식별자" 중, **대상 함수 본문에는 없고 문맥에만 새로 등장한 것**이
하나라도 있는 쌍을 셌다 (줄 단위 차이가 없는 1쌍 제외):

> **21 / 123 쌍 (17.1%)**

**나머지 83%는 같은 파일 문맥으로는 판단 근거를 얻을 수 없는 쌍이었다.**
PrimeVul의 구조상 열쇠가 되는 타입 정의·호출 규약은 대부분 **헤더나 다른 파일**에 있다.

### 그 21쌍만 따로 보면 (⚠️ 검정력 부족 — 결론에 쓰지 말 것)

| 부분집합 | T0 AUC | T1 AUC | T0 pair_rank | T1 pair_rank |
|---|---|---|---|---|
| 정보 있는 문맥 (21쌍) | 0.6032 | 0.6032 | 0.4286 | **0.6190** |
| 나머지 (103쌍) | 0.5521 | 0.5446 | 0.4563 | 0.3689 |

Δpair_rank = **+0.1905, 95% CI [+0.0000, +0.4286]** (부트스트랩 2,000회, 쌍 단위).
**신뢰구간 하한이 0이다 — 유의하지 않다.** 21쌍에서 4쌍만 뒤집혀도 나오는 크기이고,
사양서 §4-9의 최소 표본(60쌍)에 한참 못 미친다.
이 숫자는 **가설을 만들 수는 있어도 판정을 바꾸지 못한다.** §5 판정은 KILL 그대로다.

## 4. 파이프라인 버그 의심 점검

사양서 §6은 "판단 정보가 없는데 점수가 크게 움직였다면 파이프라인 버그를 의심하라"고 했다.
해당 상황이 실제로 발생했으므로(§1의 리눅스 케이스) 다음을 확인했다:

| 점검 | 결과 |
|---|---|
| T0 프롬프트가 원본 `primevul_report.jsonl`과 바이트 동일한가 | ✅ 288건 중 불일치 0 |
| T0 AUC가 v1 기존 측정치를 재현하는가 | ✅ 0.5601 vs 0.5594 (같은 248건 부분집합), 차이 0.0007 |
| 4개 arm의 케이스 집합이 동일한가 | ✅ 248건 완전 일치 |
| 쌍의 두 버전이 서로 다른 커밋에서 수집됐는가 | ✅ 같은 SHA를 쓴 쌍 0개 |
| 응답 포맷 꼬리가 arm 간 동일한가 | ✅ 문맥은 user 메시지에만 추가 |
| 12,288 토큰 상한에서 잘린 케이스 | ✅ 0건 (최대 7,281 토큰) |
| 문맥 텍스트가 원본 파일의 부분집합인가 | ✅ 29,190줄 전부 원문에 존재 |

**버그가 아니다. 긴 입력이 점수 분포를 통째로 이동시키는, 모델의 실제 성질이다.**
(V3 부록 A가 보고한 "판별력은 안정, 임계값은 불안정"의 또 다른 사례다.)

## 5. 이 절에서 얻은 재사용 가능한 관찰

1. **입력 표현을 바꾸면 운영점(τ)이 반드시 깨진다.** 문맥을 붙인 것만으로 평균 점수가
   −0.955 → −1.397로 밀렸다. 어떤 형태로든 프롬프트를 바꾸면 τ를 재보정해야 한다.
2. **정성 확인은 쌍 단위로 봐야 한다.** 케이스 단위로만 봤으면 "−3.0이나 움직였으니
   문맥이 먹혔다"고 오독했을 것이다. 쌍의 반대쪽도 −2.875 움직였다는 걸 봐야 진실이 보인다.
3. **다음 실험(T2)의 성공 조건은 "AUC가 오르는가"가 아니라
   "쌍 내부 이동량 차이가 이동량보다 커지는가"다.** 이 지표(§0의 0.198 vs 0.550)를
   T2에서 그대로 재고, 뒤집히지 않으면 그때는 진짜로 접어야 한다.
