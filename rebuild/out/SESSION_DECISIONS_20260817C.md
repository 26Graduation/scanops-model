## D-20 — 누수 규칙을 형식 실험의 **전제**로 박는다 (Phase 0 전에 기록)

**왜 필요한가.** 모든 벤치 쌍은 **취약 = 이전 판본, 안전 = 이후 판본**이다.
프롬프트에 시간 순서나 수정 의도를 흘리면, 모델이 코드가 아니라 **그 힌트로 답을 맞힐 수 있다.**
그러면 "diff 를 보여줬더니 좋아졌다"가 아니라 "정답을 알려줬더니 맞혔다"가 된다.

**규칙 (Phase 1·2 공통. 어기면 그 arm 은 무효).**

1. 두 판본은 **`Version A` / `Version B`** 중립 라벨. **어느 쪽이 A 인지 쌍마다 무작위**(seed 고정).
2. **금지어**: `previous, current, before, after, fix, fixed, patch, patched, commit, old, new, original, updated`.
   diff 블록의 제목은 **"Lines that differ between A and B"** 로 쓴다.
3. 판정은 **A·B 각각 한 번씩(양방향)**. 한 방향만 재면 어느 쪽을 물었는지가 신호가 된다.
4. **누수 검정 대조군(P-shuf)**: 라벨을 무작위로 섞은 사본에서 순위 정확도를 잰다.
   **0.55 를 넘으면 형식 자체가 라벨을 흘리는 것** → 그 arm 무효.

**이 규칙이 비싸다는 것도 적는다.** 양방향 채점이라 건수가 2배가 된다(200쌍 → 400건/arm).
그래도 한다 — **한 방향만 재면 결과를 신뢰할 수 없다.**

**무엇이 나오면 생각을 바꾸나.** P-shuf 가 0.55 를 넘으면 그 arm 을 버리고,
왜 흘렸는지(어떤 토큰/구조가 신호였는지)를 찾아 형식을 고친 뒤 다시 잰다. 기준은 낮추지 않는다.

## D-22 — pod 을 5개 만들었다. 2분 안에 4개를 지웠다 (사고 기록)

**무슨 일.** A40 이 재고 없음(`This machine does not have the resources`)으로 실패해서,
대체 GPU 를 **for 루프로 순회하며 생성 API 를 호출**했다.
루프에 "성공하면 멈춘다"가 없어서 **5개가 전부 생성됐다**
(L40S $0.99 / L40 $0.82 / A100 PCIe $1.39 / A100 SXM $1.59 / RTX A6000 $0.53 = 합계 **$5.32/hr**).

**조치.** 즉시 목록을 뽑아 **A6000($0.53) 하나만 남기고 4개를 DELETE**(전부 HTTP 204).
생성 04:57:23 ~ 04:57:31, 삭제 완료 ~04:59 — **노출 시간 약 2분, 낭비 ≈ $0.16.**

**원인은 나다.** "실패하면 다음을 시도"는 순차 폴백인데 **조기 종료 없이 루프를 돌렸다.**
생성 API 는 되돌릴 수 없는 부수효과가 있는 호출이다 — **탐색 목적으로 루프에 넣으면 안 된다.**

**앞으로.** 자원 생성 API 는 **한 번에 하나씩, 결과를 확인하고 다음으로** 간다.
가용성 탐색이 필요하면 **생성이 아니라 조회 API** 로 한다.

**왜 A6000 을 남겼나 (사고와 별개의 판단).**
Phase 1 은 **추론만** 한다(9B 4bit + 8192 컨텍스트). 48GB 면 충분하고 **$0.53/hr 로 가장 싸다.**
Phase 2(QLoRA 학습)가 필요해지면 **그때 A100 80GB 를 따로 만든다** —
v1/v3/v4 가 전부 A100 80GB·배치 8 로 학습됐고, 48GB 에서 배치를 줄이면
**"한 번에 한 변수" 규칙이 깨지기 때문**이다(레시피가 함께 바뀐다).

## D-24 — 환경 실패 1회: unsloth 설치가 torch 를 되돌려 놨다 (실행 기록)

**무슨 일.** cu128 이미지를 골라 시작은 깨끗했다(`TORCH 2.8.0+cu128 AVAIL True`).
그런데 `pip install unsloth` 가 **torch 를 2.11.0(PyPI 기본 = cu130 휠)으로 올려버렸다.**
`torchaudio 2.8.0+cu128 requires torch==2.8.0, but you have torch 2.11.0` 경고가 그대로 찍혔고,
`unsloth` import 가 `Unsloth cannot find any torch accelerator` 로 실패했다.

**어제(D-2)와 같은 부류다.** 다만 원인이 다르다 — 어제는 **이미지**가 cu130 이었고,
오늘은 **unsloth 의 의존성 해석**이 cu128 을 cu130 으로 덮었다.

**조치 (1회, 어제 검증된 조합 그대로).**
`pip install --break-system-packages --force-reinstall --no-cache-dir --index-url .../cu128
 torch==2.11.0+cu128 torchvision==0.26.0+cu128 torchaudio==2.11.0+cu128`
→ `UNSLOTH_IMPORT_OK`. **환경 실패 1회로 끝났다**(세션 규칙 상한 2회 안).

**교훈.** cu128 이미지를 고르는 것만으로는 부족하다. **unsloth 를 설치한 뒤 torch 를 다시 고정**해야 한다.
다음에는 순서를 바꾼다 — unsloth 먼저, 그 다음 torch 재고정, 그 다음 import 검증.

## D-25 — Phase 1 채점 파라미터를 바꿨고, 그것이 무엇을 바꾸는지 (실행 전 기록)

| P3 | **0.7350** | **0.8969** | **0.3592** | **+0.54** |

**P1·P3 는 "Version A 쪽을 더 취약하다고 본다"는 위치 선호를 만든다.**
전체 0.62 는 그 선호와 배정 비율(vuln=A 가 97/200)의 곱에 크게 의존한다 —
배정이 p 이면 `p·0.897+(1−p)·0.359` 이므로 p 0.4↔0.6 에서 **0.574↔0.682** 로 흔들린다.

**내 누수 검정(P-shuf)이 이걸 못 잡았다.** 라벨을 섞으면 내용 신호는 상쇄되지만
**위치 선호는 라벨과 무관해 그대로 0.5 근처**가 나온다. P3shuf 0.48 은 "누수 없음"이 아니라
"이 검정으로는 안 보임"이었다. **§4-4 설계의 결함이다.**

**결정.**
1. 계산된 판정 **`PROMPT-WIN`(P3) 을 결과로 기록한다.** 지우지 않는다.
2. **그 판정에 근거해 행동하지 않는다** — Phase 2 생략도, 제품 반영도 보류한다.
3. **판정선을 바꾸지 않는다.** 바꾸는 것은 **계측 방법**이다 — 위치 상쇄 재측정(§10-3).
   같은 200쌍을 두 배정 모두로 만들어 `acc_cb=(acc_X+acc_Y)/2` 를 주 지표로 하고,
   `pos_gap`>0.20 이면 `acc_cb` 가 높아도 `CB-NULL` 로 보낸다. 비용 약 $0.09.

**대안과 기각 이유.**
| 대안 | 기각 이유 |
|---|---|
| WIN 을 그대로 채택하고 Phase 2 생략 | **위치 편향을 diff 이해로 보고하게 된다.** 이게 오늘 가장 큰 위험이다 |
| P3 를 사후에 무효 처리 | 결과를 본 뒤 판정선을 바꾸는 것이다. 하지 않는다 |
| 재측정 없이 P2 를 고른다 | P2 도 검정되지 않은 상태다. **같은 잣대로 다시 재야 한다** |

**무엇이 나오면 생각을 바꾸나.**
- 상쇄 후에도 P3 의 `acc_cb` ≥ 0.60 이고 `pos_gap` ≤ 0.20 이면 → **진짜 개선**이다.
- 상쇄 후 `acc_cb` 가 0.5 근처로 내려가면 → **오늘의 0.62 는 전부 위치 편향**이었다.
- P2(위치 편향이 작은 arm)가 상쇄 후에도 0.53 을 넘으면 → **마커 형식이 실질 후보**다.

**되돌리는 법.** Phase 1 은 채점만 했다. 배포·가중치 변경 없음. 되돌릴 것이 없다.

**부수 확인 — D-25 의 절단 점검은 통과했다.**
어제 4096 vs 오늘 8192 의 P0: CleanVul 0.4823→0.4667(Δ −0.0156), PrimeVul 0.4082→0.4000(Δ −0.0082).
둘 다 ±0.05 이내 → **절단이 어제 결과를 만들고 있던 것이 아니다.**

**하나 더 — 동점률이 형식으로 크게 줄었다.** P0 0.33 → P1 0.045 / P3 0.035.
**diff 를 보여주면 모델이 최소한 "두 판본을 다르게 본다".** 방향이 맞는지는 별개 문제이고,
그것이 §10 이 재려는 것이다.

## D-28 — 기준선을 재서 **2×2 분해**가 가능해졌다 (Phase 2 결과 전 기록)

`v3_s42_step750` 을 Phase 1 과 **같은 세트·같은 채점 조건**으로 채점했다(A6000, $0.09).

| 모델 | P0 (현행 형식) | P2 (상쇄) | P1 (상쇄) |
|---|---|---|---|
| **v1** (배포) | 0.4600 (동점 0.3300) | **0.6050** (gap 0.090, 동점 0.155) | 0.5800 (gap 0.430) |
| **v3s42@750** | **0.3400** (동점 **0.5200**) | 0.5800 (gap 0.150, 동점 0.260) | 0.5075 (gap 0.385) |

**v3s42@750 은 이 과제에서 v1 보다 못하다.** 특히 P0 에서 **동점률이 0.52** 다 —
쌍의 절반 이상에 **소수점까지 같은 점수**를 준다.
P2 상쇄 기준 Δ(v3s42 − v1) = **−0.0250 [−0.0825, +0.0325]** (CI 가 0 을 포함).

**이 사실이 Phase 2 의 비교 구조를 정한다.** 이제 2×2 로 분해할 수 있다:

| | 추론 형식 P0 | 추론 형식 P2 |
|---|---|---|
| **표준 형식 학습** (v3s42@750) | **0.3400** | **0.5800** |
| **P2 형식 학습** (v5@750) | ? (전이) | ? (본 조건) |

- `v3s42+P2 = 0.5800` 이 **"추론 때만 형식을 바꿨을 때"** 의 값이다.
- 따라서 **v5+P2 가 0.5800 을 넘어야 "학습이 기여했다"** 고 말할 수 있다.
  단순히 v3s42+P0(0.3400) 과 비교하면 **학습 기여와 추론 형식 기여가 섞인다.**

**그래서 판정에 쓸 대조를 여기서 고정한다 (결과 전).**

| 묻는 것 | 대조 |
|---|---|
| **형식 학습이 기여했는가** | v5+P2 **vs v3s42@750+P2 (0.5800)** ← 주 대조 |
| 형식 전체(학습+추론)의 효과 | v5+P2 vs v3s42@750+P0 (0.3400) |
| 형식이 전이되는가 | v5+P0 vs v3s42@750+P0 (0.3400) |
| 제품 관점 | v5+P2 vs **v1+P2 (0.6050)** — 배포 중인 것을 이겨야 바꾼다 |

**사양 §5 의 ADOPT-PR 판정선(0.60)은 그대로 둔다.** 바뀐 것은 **무엇과 비교하는지**이고,
그 이유는 "학습 기여만 떼어 보려면 추론 형식을 맞춰야 한다"는 것이다.

**무엇이 나오면 생각을 바꾸나.**
- v5+P2 ≈ 0.58 이면 → **학습은 기여하지 않았다.** 형식은 추론에서만 쓰면 된다(= 코드 한 줄).
- v5+P2 가 0.58 을 넘고 v1+P2(0.6050)도 넘으면 → 학습 기여가 있고 제품에도 쓸 만하다.
- v5+P0 가 v3s42+P0(0.3400)보다 크게 오르면 → 형식 학습이 **형식 없이도** 도움이 된 것이다(뜻밖의 이득).

**덧붙임 — v3s42 의 동점률 0.52 는 그 자체로 기록해 둘 값이다.**
어제 v4 세션에서 v3s42 를 "기준선"으로 여러 번 썼는데,
**이 과제(0.95+ 쌍)에서는 절반 이상을 구분조차 못 하는 상태**였다.
