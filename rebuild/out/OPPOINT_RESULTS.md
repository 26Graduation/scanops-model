## §1 `PRECISION-UNREACHABLE` 이 정확히 무슨 뜻인가

**정확한 서술은 이것뿐이다:**

> CleanVul_v2 분포에서 v1 의 AUC(report **0.6165**)가 주는 precision 상한이 0.70 아래다.
> tune 에서 사전등록 규칙("precision ≥ 0.70 중 recall 최대")으로 고른 **τ = 1.375** 를
> report 에 1회 적용한 결과 **precision 0.6465 [95% CI 0.6084–0.6877], recall 0.1419** 였다.

**이 문장에서 "CleanVul_v2 분포에서"를 떼면 틀린 문장이 된다.** §0 표대로 다른 벤치에서는 넘는다.

### §1-1 "상한"의 두 층 — 포락선과 실측

**(a) AUC 가 주는 포락선.** ROC 가 오목하면 Youden J = TPR − FPR ≤ 2·AUC − 1 이다
(오목 ROC 는 (0,0)–(f,t) 와 (f,t)–(1,1) 두 현 위에 있으므로 AUC ≥ (1+t−f)/2).
균형셋(50:50)에서 precision = TPR/(TPR+FPR) 이므로 recall t 에서
`FPR ≥ max(0, t − J)` → `precision ≤ t / (t + max(0, t − J))`.

| 벤치 | AUC | J 상한 | recall 0.75 에서 precision 상한 | recall 0.50 | recall 0.30 |
|---|---|---|---|---|---|
| 내부 test | 0.9052 | 0.8104 | 0.9926 | 1.0 | 1.0 |
| CyberNative 154 | 0.9126 | 0.8252 | 1.0 | 1.0 | 1.0 |
| CVEfixes 157 | 0.8732 | 0.7464 | 0.9926 | 1.0 | 1.0 |
| CleanVul_v2 report | 0.6165 | 0.2330 | **0.5919** | 0.6522 | 0.8174 |
| PrimeVul report | 0.5618 | 0.1236 | **0.5445** | 0.5701 | 0.6296 |

> **이 포락선만으로 "precision 0.70 은 불가능"이라고 쓰면 틀린다.**
> 낮은 recall 에서는 포락선이 1.0 까지 열린다(CleanVul 은 recall ≤ 0.233 이면 이론상 precision 1.0 가능).
> AUC 는 **높은 recall 쪽을 막을 뿐**이다. 그래서 실측 곡선을 함께 본다.

**(b) 실측 곡선 전수 검사** (사후 참고 — 판정에는 쓰지 않음, `out/oppoint_envelope_v1.json`):

| 벤치 | `precision ≥ 0.70 AND recall ≥ 0.10` 인 τ | `recall ≥ 0.75 AND FPR ≤ 0.15` 인 τ | recall ≥ 0.75 에서 최대 precision |
|---|---|---|---|
| 내부 test | **37개** | **3개** | 0.8525 |
| CyberNative 154 | **47개** | **3개** | 0.8824 |
| CVEfixes 157 | **26개** | **1개** | 0.8472 |
| CleanVul_v2 report | **0개** | **0개** | 0.5557 |
| PrimeVul report | **0개** | **0개** | 0.5330 |

**이것이 `PRECISION-UNREACHABLE` 의 실증적 내용이다.**
CleanVul/PrimeVul 에서는 사전등록한 한 점에서만 미달한 것이 아니라 **곡선 전체에 그런 점이 없다.**
같은 검사를 다른 세 벤치에 돌리면 26~47개가 나온다 — **도구나 채점기의 문제가 아니다.**

### §1-2 이 상한을 만든 것은 **두 가지이고, 둘 다 적는다**

**(1) 벤치가 재는 질문이 다르다.** `FINAL_ARCHITECTURE_REPORT.md` §4 실측:
CleanVul 쌍의 **38% 가 동일 슬라이스**(같은 코드가 취약·안전 양쪽에 등장),
**54% 가 비-sanitizer 패치**(리팩터·널체크 등). 라벨이 묻는 것은 "이 코드가 취약한가"보다
**"이 변경이 취약점을 고치는 변경인가"** 에 가깝다.
PrimeVul 도 같은 계열(커밋 쌍)이며 v1 AUC 0.5618 로 더 낮다.

**(2) 모델의 판별력이 그 질문 앞에서 부족하다.** 같은 모델·같은 채점기·같은 프롬프트로
위 세 벤치에서는 AUC 0.87~0.91, 아래 두 벤치에서는 0.56~0.62 다.
**이걸 전부 벤치 탓으로 넘길 수 없다.** 커밋 쌍 구분은 실제 코드리뷰가 요구하는 능력이고,
v1 은 그 능력을 가지고 있지 않다.

**두 원인은 함께 작용한다. 한쪽만 적으면 사실과 다르다.**

> **이번 5종 측정이 앞선 서술을 하나 정정한다.**
> 이전 문서들은 이 격차를 "도메인 밖 일반화 실패(내부 0.905 vs 외부 0.56~0.62)"로 적었다.
> CyberNative 154 는 **학습 코퍼스와 무관한 독립 출처**인데 AUC **0.9126** 이다.
> 따라서 "외부면 무너진다"는 서술은 이번 측정과 맞지 않는다.
> 다만 아래 §1-3 의 할인 사유 때문에, **낙관하는 것도 근거가 부족하다.**
> **§1-4 에서 그 축을 특정했다 — 평가셋이 쌍(같은 커밋의 취약본·패치본)인가 아닌가다.**
> 그리고 §1-4 는 위 (2)를 더 정확하게 만든다: 내부 test 는 **쌍 벤치가 아니므로**
> "내부 0.905 vs 외부 0.62" 비교에는 **분포 차이만이 아니라 과제 차이가 섞여 있다.**

### §1-3 두 레거시 벤치를 할인해서 읽어야 하는 이유

| 벤치 | 누수 검사 결과 | 그럼에도 할인하는 이유 |
|---|---|---|
| CVEfixes 157 | train_v3+val_v3 대비 **정규화 코드 해시 겹침 0**, **CVE ID 겹침 0/157** | 학습 데이터의 **71%(10,404/14,895)가 같은 CVEfixes 코퍼스**다. 게다가 **내부 test 와 CVE 25개를 공유**한다. 학습에 들어가지 않았을 뿐 **같은 코퍼스 계열**이며, 독립 도메인이 아니다 |
| CyberNative 154 | 동일 검사 겹침 0. 출처가 CVEfixes 와 무관 | **합성 데이터**다(7개 언어 × 22건, 결함이 하나씩 심어진 정제 함수). 실제 저장소 코드보다 쉽다. n=154 로 CI 가 넓다(예: OP-0 precision 0.9123 [0.836–0.982]) |

**근사 중복은 두 검사 모두 못 잡는다.** 완전일치 해시·CVE ID 기준이라는 한계를 그대로 적는다.

### §1-4 쌍 판별력 분해 — **한 번 잘못 읽었고, 다시 재서 고쳤다**

`rebuild/pair_discrimination.py` / `out/pair_discrimination_v1.json`. 비용 $0.

> **먼저 정정.** 이 절의 첫 판(커밋 `60c3b8d`)에서 나는
> *"내부 test 는 쌍 벤치가 아니다(pair_id 0/1,197) → 내부 AUC 0.9052 는 쌍 판별 증거가 아니다"* 라고 썼다.
> **틀렸다.** 내부 test 는 구버전 빌더로 만들어져 `pair_id` **필드**가 없을 뿐,
> **같은 CVE 의 취약본·패치본이 둘 다 들어 있다**(641 CVE 중 496개, 정확히 1:1 인 것 472쌍).
> `cve_id` 로 다시 묶어 재측정한 것이 아래 표다. **결론이 바뀌었다.**

**모델은 쌍을 구분할 수 있다 — 어떤 쌍이냐에 따라.** 내부 CVEfixes 쌍에서는 0.9068 이고,
PrimeVul 쌍에서는 0.4931(우연 아래), CleanVul 쌍에서는 0.5558 이다.

#### 이 표가 **기각하는** 설명 두 가지

**(1) "쌍 형식 학습 데이터가 없어서" — 기각.** 학습셋이 이미 쌍이다.

| split | 항목 | 1:1 쌍 | 쌍 항목 비율 | 출처 |
|---|---|---|---|---|
| `train_v3` | 13,406 | 5,533 | **82.5%** | cvefixes 9,191 (68.6%) / primevul 4,162 (**31.0%**) / cleanvul 53 |
| `val_v3` | 1,489 | 548 | 73.6% | cvefixes 1,213 / cleanvul 120 / primevul 156 |

**(2) "학습 분포 밖이라서" — 이것도 잘 맞지 않는다.**
**PrimeVul 은 학습 항목의 31.0%(쌍 2,081개)를 차지하는 코퍼스**다. 그 홀드아웃 쌍에서 0.4931 이다.
반면 CleanVul 은 학습에 **53건(0.4%)** 뿐인데 0.5558 로 **더 낫다.**
"많이 본 코퍼스일수록 잘한다"가 성립하지 않는다.

#### 그래서 지금 말할 수 있는 것

**쌍 판별 성능이 코퍼스별로 갈린다: CVEfixes 0.9068 vs PrimeVul 0.4931.**
두 코퍼스 모두 학습에 들어 있고, 형식도 같다(같은 커밋의 취약본·패치본).

**남는 후보 설명 — 오늘 측정으로 구분하지 못한다. 가설로 적는다.**

| 가설 | 이 데이터와 일관되는가 | 어떻게 검정하나 |
|---|---|---|
| **CVEfixes 쌍에 표면 단서가 있다** (패치가 눈에 띄는 형태 — 경계검사 추가 등) — 모델이 그 단서를 학습했고, 그 단서가 없는 PrimeVul 에서 무너진다 | 일관. PrimeVul 은 논문이 **그런 인공물을 걷어내려고** 엄격 검수한 세트다 | CVEfixes 쌍에서 diff 유형별 순위 정확도 분해. 패치 유형이 단순한 쌍에서만 높으면 지지 |
| **PrimeVul 이 그냥 더 어렵다** (C/C++ 전용·미묘한 결함) | 일관. §3-4 언어별 표에서도 C/C++ 가 최저 | 다른 C/C++ 쌍 세트에서 재측정 |
| **목적함수가 쌍 순서를 강제하지 않는다** | **부분적으로만.** 그 설명이 맞다면 CVEfixes 쌍에서도 낮아야 하는데 0.9068 이다. 완전한 설명은 아니다 | 쌍 대조 목적함수로 1회 학습, 판정은 **홀드아웃 쌍 순위 정확도** |

**셋 중 무엇인지 오늘은 모른다. 모른다고 적는다.**

### §1-4b 원인 규명 1단계 — **표면 단서 가설은 지지된다. 다만 코퍼스 격차를 다 설명하지는 못한다**

§1-4 가 남긴 세 가설 중 H1(표면 단서)·H2(난이도)를 **학습 없이** 검정했다.
`rebuild/pair_cue_analysis.py` / `out/pair_cue_v1.json`. 비용 **$0**.

쌍마다 **패치 diff 라인 수**와 **패치본에만 추가된 방어 토큰**(`if/check/valid/bound/len/null/…`)을
재고, 쌍 내 순위 정답 여부와 대조했다.

#### (1) H1 예측 — 전부 맞았다

| 벤치 | 쌍 | 순위 정확도 | **정답 쌍 diff 중앙값** | **오답 쌍 diff 중앙값** | 방어토큰 추가 시 순위 | 미추가 시 |
|---|---|---|---|---|---|---|
| 내부 test (CVEfixes) | 472 | 0.9068 | **30** | **9** | **0.9689** | 0.8502 |
| CleanVul_v2 report | 1,353 | 0.5558 | **5** | **4** | **0.7128** | 0.5294 |
| PrimeVul report | 144 | 0.4931 | **6** | **3** | 0.4167 (n=12) | 0.5000 |

**세 벤치 모두 "정답 쌍의 패치가 오답 쌍보다 크다".**
diff 구간별로 보면 단조 증가한다:

| diff 라인 | 내부 test | CleanVul_v2 | PrimeVul |
|---|---|---|---|
| 0–5 | 0.7869 (n=61) | 0.5138 (n=798) | **0.3953** (n=86) |
| 6–20 | 0.8806 (n=134) | 0.6088 (n=432) | 0.6744 (n=43) |
| 21–60 | 0.9474 (n=152) | 0.6226 (n=106) | 0.5000 (n=14) |
| 61+ | 0.9440 (n=125) | 0.7647 (n=17) | 1.0 (n=1) |

**→ 모델의 쌍 판별은 상당 부분 "패치가 얼마나 눈에 띄는가"에 실려 있다.**
CleanVul 에서 방어 토큰이 추가된 쌍의 순위 정확도는 0.7128 인데, 안 된 쌍은 0.5294(우연 수준)다.

#### (2) 코퍼스마다 패치의 성격이 다르다 — 이것이 0.9068 vs 0.4931 의 큰 부분이다

| 벤치 | diff 라인 중앙값 | **방어 토큰 추가 비율** |
|---|---|---|
| 내부 test (CVEfixes) | **26** | **47.7%** |
| CleanVul_v2 report | 4 | 14.4% |
| PrimeVul report | 4 | 8.3% |

**CVEfixes 패치는 중앙값 26라인이고 절반이 방어 토큰을 추가한다.
PrimeVul 패치는 4라인이고 8%만 그렇다.** 같은 "커밋 쌍"이라도 재는 것이 다르다.

#### (3) 그러나 diff 크기를 맞춰도 격차가 남는다 — H1 만으로는 부족하다

같은 **0–5 라인** 구간에서: 내부 test **0.7869** vs CleanVul **0.5138** vs PrimeVul **0.3953**.
**작은 패치만 놓고 비교해도 코퍼스 격차가 그대로 있다.**
따라서 H2(코퍼스 자체 난이도) 또는 아직 이름 붙이지 않은 요인이 함께 작용한다.

#### (4) 누수는 아니다 (확인함)

내부 test 는 train+val 대비 **CVE ID 겹침 1/641(0.16%)**, **정규화 코드 해시 겹침 0** 이다.
0.9068 은 학습 데이터를 다시 본 결과가 아니다.

#### (4b) 2단계 — **동시 통제**와 **토큰 목록 민감도** (`pair_cue_joint.py`, $0)

§1-4b (1)~(3)은 diff 크기와 방어 토큰을 **따로** 봤다. 둘을 **동시에** 통제하고,
방어 토큰 목록도 넓은 것/좁은 것 두 벌로 돌렸다.

**(A) (diff 구간 × 방어토큰) 셀 안에서도 코퍼스 격차가 그대로 남는다.**

| 셀 | 내부 test | CleanVul_v2 | PrimeVul |
|---|---|---|---|
| diff 0–5, 방어토큰 없음 | **0.7679** (56) | **0.5000** (714) | **0.4177** (79) |
| diff 6–20, 방어토큰 없음 | 0.8444 (90) | 0.5782 (358) | 0.6667 (42) |
| diff 21+, 방어토큰 없음 | 0.9010 (101) | 0.5698 (86) | 0.4545 (11) |
| diff 0–5, 방어토큰 있음 | 1.0 (5) | 0.6310 (84) | 0.1429 (7) |
| diff 6–20, 방어토큰 있음 | 0.9545 (44) | 0.7568 (74) | 1.0 (1) |
| diff 21+, 방어토큰 있음 | 0.9716 (176) | 0.8108 (37) | 0.75 (4) |

**표본이 충분한 셀에서 순서가 항상 내부 test > CleanVul > PrimeVul 이다.**
→ **"표면 단서"는 코퍼스 격차를 설명하지 못한다.** 두 요인은 별개다.

**(B) 방어 토큰 효과는 diff 구간 안에서도 살아남는다** — CleanVul 기준
0–5라인 0.500→0.631, 6–20라인 0.578→0.757, 21+라인 0.570→0.811.
크기 효과와 별개의 신호다.

**(C) 그러나 토큰 목록에 민감하다 — 그대로 적는다.**

| 벤치 | 넓은 목록(추가/미추가) | 좁은 목록(추가/미추가) |
|---|---|---|
| 내부 test | 0.9689 / 0.8502 | 0.9867 (n=75) / 0.8917 |
| CleanVul_v2 | 0.7128 / 0.5294 | **0.5833 (n=24) / 0.5553** ← 효과 거의 사라짐 |
| PrimeVul | 0.4167 (n=12) / 0.5000 | 0.5000 (n=2) / 0.4930 |

좁은 목록(`assert/sanitiz/escape/encode/…`)만 쓰면 CleanVul 의 효과가 거의 사라진다(n=24).
**즉 넓은 목록이 잡은 것은 "sanitizer 추가"라기보다 `if/len/size/null` 같은
일반적 어휘 변화**일 가능성이 크다. **"방어 코드 추가"라고 부르면 과대 해석이다.**
아래 (5)에서는 **"어휘 변화 폭"** 이라는 더 약한 이름을 쓴다.

#### (5) 결론 — 말할 수 있는 것 / 없는 것

- **말할 수 있다 (1):** **패치 크기**는 세 벤치 모두에서 쌍 판별 정답률을 예측한다. 단조 증가하고,
  방어 토큰 유무를 통제해도 유지된다. CVEfixes 패치는 중앙값 26라인, PrimeVul 은 4라인이다.
- **말할 수 있다 (2):** 패치본의 **어휘 변화 폭**(넓은 토큰 목록 기준)도 예측력이 있다 —
  CleanVul 에서 diff 구간을 통제해도 0.5→0.63, 0.58→0.76, 0.57→0.81 로 오른다.
- **말할 수 없다 (1):** 그것이 **"sanitizer 를 추가했는가"** 라는 것.
  좁은 목록으로 바꾸면 CleanVul 의 효과가 사라진다(n=24). 어휘 변화의 대리 지표일 뿐이다.
- **말할 수 없다 (2):** 그것이 **인과**라는 것. 이 분석은 예측 대조다.
- **말할 수 없다 (3):** **코퍼스 격차의 원인.** diff 구간과 토큰을 **동시에** 통제해도
  내부 test > CleanVul > PrimeVul 순서가 유지된다. **가장 큰 항이 설명되지 않은 채 남아 있다.**
- **대외 자료에 쓸 때:** "내부 test 쌍 판별 0.9068" 을 인용하려면
  **"그 벤치의 패치가 중앙값 26라인이고 47.7% 가 방어 코드를 추가한다"** 를 같이 적어야 한다.
  그것 없이 인용하면 모델의 능력을 과대 표현하게 된다.

### §1-5 반대 방향으로 측정된 사실 — 빠뜨리지 않는다

`DOSE_RESULTS.md`: **같은 CleanVul 벤치**에서 학습량을 step 450 → 750 으로 늘리자
AUC 가 **+0.019 올랐고 부트스트랩 CI 가 0 을 배제**했다.

따라서 **"벤치가 이상해서 학습이 무의미하다"는 결론은 데이터와 어긋난다.**
이 벤치는 학습에 반응한다. 다만 반응 폭이 목표선까지 가기에 작다.

## §2 운영점 재보정 (사양 §8)

### §2-0 배포 경로의 임계값은 암묵적이었다

배포(`scripts/api_rebuild.py` → `_detect`)는 greedy 생성이다.
greedy 는 `logP(" CWE") > logP(" NONE")`, 즉 **τ = 0** 을 쓰고 있다. 고른 적이 없다.

**OP-0 ≡ greedy 확인 (실측 일치율):**

| 벤치 | n | τ=0 판정 ↔ 저장된 argmax 라벨 일치 | 일치율 |
|---|---|---|---|
| 내부 test | 1,197 | 1,183 | **0.9883** |
| CleanVul_v2 report | 2,706 | 2,614 | **0.9660** |
| PrimeVul report | 288 | 274 | **0.9514** |
| CVEfixes 157 | 157 | 155 | **0.9873** |
| CyberNative 154 | 154 | 152 | **0.9870** |

100% 가 아닌 이유는 동점·파싱 경계다. **"OP-0 은 현 배포와 같은 지점"은 근사이며 오차는 위 표만큼이다.**
(토큰 ID 확인: `' NONE' → 41451`, `' CWE' → 49149`.)

### §2-0b 서빙 경로 실측 대조 — **오프라인 τ 는 그대로 서빙에 옮길 수 없다**

위 §2-1~§2-3 의 모든 τ 는 **오프라인 점수**(unsloth 4bit, `score_logprob.py`)에서 골랐다.
실제 배포는 **llama-server + `Qwen3.5-9B-Q4_K_M.gguf` + `adapter_v1_fix.gguf`** 다.
같은 것을 재는지 직접 확인했다(`rebuild/verify_serving_score.py`, 내부 test 20건, 로컬 $0):

| 항목 | 값 |
|---|---|
| 토큰 ID 검증 | **일치** (`' CWE' → 49149`, `' NONE' → 41451`) |
| 판정(τ=0) 일치율 | **0.95** (19/20) |
| 점수 순위상관 (Spearman) | **0.9865** |
| 점수 반환 실패(None) | 0건 |

**→ 서빙 경로는 오프라인과 같은 것을 재고 있다.** 운영점 분석이 배포와 무관한 숫자가 아니라는 확인이다.

**그러나 절대값은 계통적으로 어긋난다:**

| | 평균 편차 (서빙 − 오프라인) |
|---|---|

**양자화(Q4_K_M)가 음수 쪽 점수를 0 방향으로 압축한다.**
τ=0 판정이 잘 맞는 이유는 대부분의 항목이 0 에서 멀기 때문이지, 점수 척도가 같아서가 아니다.

> **따라서: 오프라인에서 고른 τ(예: OP-B 의 1.0)를 `SCANOPS_TAU` 에 그대로 넣으면 안 된다.**
> τ 를 도입하려면 **서빙 경로에서 다시 골라야 한다.**
> 이번에는 `OP-INSUFFICIENT` 라 τ 를 도입하지 않으므로 이 문제가 발생하지 않는다.
> **τ 를 쓰기로 결정하는 날, 이 항목이 먼저 해결돼야 한다.**
> (n=20 으로 잰 편차다. 도입 시에는 더 큰 표본으로 다시 잰다.)

### §2-3 판정 (사양 §8-6)

조건 ① 내부 test `recall ≥ 0.75 AND FPR ≤ 0.15`, ② CleanVul_v2 report Δprecision(vs OP-0) **CI 하한 > 0**.

| OP | ① 내부 test | ② CleanVul Δprecision vs OP-0 [CI] | 통과 |
|---|---|---|---|
| OP-A | ✗ (R 0.948 / FPR 0.378) | **−0.0767** [−0.093, −0.062] | ✗ |
| OP-B | ✗ (R 0.638) | **+0.0145** [−0.008, +0.037] | ✗ |
| OP-C | ✗ (R 0.565) | **+0.0131** [−0.017, +0.043] | ✗ |

→ **`OP-INSUFFICIENT`. 배포 운영점을 바꾸지 않는다.** (`SCANOPS_TAU` 를 설정하지 않는다 = 현행 greedy 유지)

**이 표가 말하는 것 (측정된 것만):**

1. **임계값을 올려도 CleanVul precision 이 유의하게 오르지 않는다.**
   OP-B 는 +0.0145 이고 CI 가 0 을 포함한다. 대가로 recall 이 0.4435 → 0.2203 으로 **반토막** 난다.
   남는 거래가 아니다.
2. **내부 test 에는 (R ≥ 0.75, FPR ≤ 0.15) 를 만족하는 τ 가 3개 존재한다**(§1-1b).
   그런데 사전등록 규칙으로 고른 OP-B/C 는 거기 있지 않다. **왜 그런지를 직접 확인했다**
   (사후 참고, `out/oppoint_tau_conflict.json` — 판정에는 쓰지 않는다):

   | τ 를 어디서만 골랐나 | τ | 내부 test recall / FPR | CleanVul report precision / recall |
   |---|---|---|---|
   | CleanVul tune 단독, FPR ≤ 0.15 | 1.000 | 0.6377 / 0.073 | 0.6274 / 0.2203 |
   | **내부 val 단독, FPR ≤ 0.15** | 0.625 | **0.7373** / 0.101 | 0.6281 / 0.2846 |
   | 내부 val 단독, FPR ≤ 0.10 | 1.000 | 0.6377 / 0.073 | 0.6274 / 0.2203 |

   **"두 소스를 함께 걸었기 때문"이라는 설명은 부정확하다.**
   도메인 안 소스(val)만 써도 F1-최대 규칙은 τ=0.625 를 고르고, 그때 내부 test recall 은
   **0.7373 으로 게이트 0.75 를 아슬하게 못 넘는다.** 발목을 잡는 것은 두 분포 충돌이 아니라
   **FPR ≤ 0.15 제약 자체**와, val→test 로 넘어갈 때의 선정 이월 손실이다.

3. **CleanVul 에서 precision 은 τ 에 거의 반응하지 않는다.** 이것이 더 근본적이다.

   | recall 하한 | CleanVul report 최대 precision | 내부 test 최대 precision |
   |---|---|---|
   | ≥ 0.75 | 0.5557 | 0.8525 |
   | ≥ 0.50 | 0.5959 | 0.9049 |
   | ≥ 0.30 | 0.6308 | 0.9421 |
   | ≥ 0.10 | **0.6465** | 1.0000 |

   recall 을 0.75 → 0.10 으로 **7.5배 포기해도 precision 은 +0.09 오르고 0.70 에 닿지 않는다.**
   같은 표에서 내부 test 는 0.8525 → 1.0 으로 가파르게 오른다.
   **CleanVul 에서는 임계값이 살 수 있는 precision 이 거의 없다** — 이것이 `PRECISION-UNREACHABLE` 의 실체다.
4. **OP-0(현 배포)이 이미 나쁘지 않은 선택이었다.** 내부 test F1 0.8054 는 네 OP 중 최고이고,
   CleanVul precision 0.6129 도 OP-A 보다 높다. 고른 적 없는 임계값이었지만, 바꿀 이유가 이번 측정에는 없다.
5. 이 결과는 오늘의 다른 측정과 **모순되지 않는다.** `SC_INFO`·`DOSE`·부록 A 는
   "관측된 변동이 운영점 이동으로 설명된다"고 말했다 — 그건 **변동의 원인**에 대한 진술이다.
   이번 측정은 **그 운영점을 골라도 외부 precision 은 사지 못한다**는 별개의 사실이다.
   임계값은 판별력(AUC)을 바꾸지 않기 때문에 둘은 양립한다.

## §3 한계 (측정하지 않은 것)

- **유병률.** 모든 표는 50:50(또는 근접) 균형셋이다. 실제 PR 트래픽은 그렇지 않다.
  유병률이 낮으면 같은 (recall, FPR)에서 precision 은 **더 낮다.** 이 보정은 재지 않았다.
  **"오탐률"을 유병률 없이 인용하지 않는다.**
- **내부 val 과 내부 test 는 같은 분포다.** 내부 test 숫자는 낙관적이다.
- **레거시 벤치 2종은 §1-3 의 사유로 할인해야 한다.** n=154/157 로 CI 가 넓다.
- **근사 중복 누수는 검사하지 않았다.** 완전일치 해시·CVE ID 기준까지만 쟀다.
- **v1 한 모델·한 시점.** v4 가 `ADOPT` 되면 같은 규칙으로 다시 잰다(사양 §8-7).
- §1-1(b) 의 곡선 전수 검사는 **사후 참고**다. 판정은 사전등록한 τ 로만 했다.
