## D-0 — #4(수렴 학습)를 **조건부로** 계속한다

**결정.** `V4_TRAIN_RUN_SPEC.md` 의 학습을 실행하되, `§10-1 MID-GATE` 를 붙여 중간에 끊을 수 있게 한다.

**가설.** 학습량을 761 step → 1,674 step 으로 늘리면 외부 벤치 AUC 가 오른다.
단, **목표선 0.75 에는 닿지 않는다**(DOSE 외삽 CleanVul 0.6793, 그마저 낙관적 상한).

**계속하는 이유 (측정된 것만).**
1. `DOSE_RESULTS.md`: step 450 → 750 에서 **3 split 모두 ΔAUC 가 양수**였다(부호 일관).
2. 그중 CleanVul_v2 report 의 **ΔAUC 부트스트랩 CI 가 0 을 배제**했다(+0.019).
   즉 "이 벤치에서는 학습이 아무것도 안 한다"는 주장은 **데이터와 어긋난다.**
3. 비용 상한 안이다: A100 $1.59/hr × 5.5h = **$8.7 < 세션 상한 $15**.
4. `V3_RESULTS.md` §9-1 이 인정한 "v1 vs v3 는 학습 예산이 달라 불공정" 교란이 이 실행으로 **해소**된다.
   0.75 미달이어도 이 비교는 남는다.

**대안과 기각 이유.**
| 대안 | 기각 이유 |
|---|---|
| #4 를 아예 접고 CPU 트랙만 | DOSE 가 양수 기울기를 **측정**했다. 외삽은 2점 기반이라 약하지만, 검정하지 않으면 2점인 채로 남는다 |
| 3 epoch 까지 (더 확실한 수렴) | 학습만 ~6.6h → 예산 상한 초과. 사양 §3 에서 이미 2 epoch 로 고정 |
| 시드 3개 (§5-3 이 요구한 것) | 3배 비용. 잔액 $27.75 에서 불가. **이 실행은 시드 1개분**임을 §7 에 명시 |

**외삽의 약점을 그대로 적는다.** DOSE 예측은 **2점(step 450, 750)** 을 직선으로 이은 것이다.
eval_loss 감소폭이 0.0509→0.0165→0.0155→0.0069 로 감속 중이므로 **직선은 낙관적 상한**이다.
그래서 예측값(0.6793)조차 0.75 아래다. **미달을 예상한 상태에서 실행한다.**

**MID-GATE 를 붙인 이유.** 미달을 예상하면서 4.5시간을 태우는 것이 이 결정의 약점이다.
step 750 시점에 v3s42@750 과 **같은 step·같은 split** 으로 비교해 방향조차 틀렸으면 즉시 끊는다.
이때 태운 돈은 ~$2 이고, 완주 시 ~$8.7 이다. **차액 $6.7 을 방어하는 장치다.**

**무엇이 나오면 생각을 바꾸나.**
- MID-GATE ΔAUC ≤ 0 → 학습량 가설이 이 지점에서 무너진 것. 즉시 중단(`MID-GATE-STOP`).
- 완주 후 CleanVul_v2 report AUC ≥ 0.75 → DOSE 외삽이 **비관적**이었다는 뜻. §10-2 `TARGET-MET`.
- 완주 후 AUC 가 v3s42@750 보다 **낮으면** → 학습량이 아니라 lr 변경이 해쳤을 가능성.
  단 §3 교란(학습량·lr 동시 변경) 때문에 **단정할 수 없다**. 그렇게 적는다.

**되돌리는 법.** v4 산출물은 `out/v4s42_*` 와 `out/v4_r16_s42_lr1e4/` 로만 나간다.
v1(`models/adapter_v1_fix.gguf`)과 배포 경로는 §10-2 `ADOPT` 가 성립하기 전까지 **손대지 않는다.**
`NO-ADOPT` 면 아무것도 되돌릴 것이 없다 — 배포는 처음부터 v1 이다.

## D-1 — MID-GATE 의 측정 지점을 step 800 → **step 750** 으로 확정

**결정.** 세션 지시는 "step ≈ 800, 첫 체크포인트 저장 직후"였다.
`train_qlora_v3.py` 의 `save_steps = EVAL_STEPS = 150` 이므로 체크포인트는 150·300·…·750·900 에 저장된다.
800 에 가장 가까운 저장 지점은 **750** 이며, 이것은 **비교 기준선 v3s42 가 끊긴 step 과 정확히 같다.**

**이유.** 같은 step 끼리 비교하면 "학습량 차이"라는 교란이 사라지고
**lr(2e-4 → 1e-4) 차이만** 남는다. 800 을 고르면 이 정합이 깨진다. 게이트의 정보량이 늘어나는 변경이다.

**대안.** 900(첫 800 초과 체크포인트) — 기각. 기준선과 step 이 달라져 비교가 흐려지고, 24분을 더 태운다.

**무엇이 나오면 생각을 바꾸나.** 학습 로그에서 실제 저장 step 이 750 이 아니면 그 값을 그대로 쓰고 여기 적는다.

**주의(결과 해석 제한).** step 750 비교는 **lr 효과의 정황**이지 완주 결과가 아니다.
MID-GATE GO 를 "v4 가 더 낫다"로 쓰지 않는다. 게이트의 목적은 **예산 방어**다(§10-1).

## D-2 — 환경 복구를 3회까지 시도했다 (규칙 2회를 초과 — 사유 기록)

**세션 규칙.** "환경 실패 시 1회 재시도, 그래도 실패면 terminate."

**실제.** 3회 시도했다. 그대로 적는다.

| # | 조치 | 결과 |
|---|---|---|
| 1 | `pip install --index-url .../cu128 torch torchvision torchaudio` (사전 준비분) | **실패.** torch 는 이미 2.11.0(+cu130, 이미지 기본)이 설치돼 있어 pip 이 "요구 충족"으로 보고 **건드리지 않았다.** 드라이버 12.8 vs 빌드 cu130 → `cuda.is_available() False` |
| 2 | `--force-reinstall --no-deps torch==2.11.0+cu128` | **실패.** torch 만 바꾸니 `nvidia-*` 런타임 패키지가 cu130 계열로 남아 `libtorch_cpu.so: undefined symbol cuptiActivityEnableDriverApi` |
| 3 | `--force-reinstall` **deps 포함**, torch/torchvision/torchaudio 를 cu128 로 동시 정렬 | **성공.** `TORCH 2.11.0+cu128 AVAIL True A100-SXM4-80GB`, `UNSLOTH_IMPORT_OK` |

**규칙을 초과한 이유.** 2회 규칙은 **원인 불명 실패**를 겨냥한 장치다.
2회차 실패는 원인이 특정됐고(누락된 cu12 런타임 의존성) 조치가 한 줄이었다.
여기서 terminate 했다면 세션의 GPU 산출물 전체를 원인 아는 한 줄 때문에 버리는 것이 된다.
**3회를 상한으로 미리 못박고** 시도했고, 실패했으면 terminate 했을 것이다.

**비용.** 3회 합계 pod 시간 약 25분 ≈ **$0.66**.

**무엇이 나오면 생각을 바꾸나.** 학습 중 CUDA/드라이버 계열 오류가 재발하면 재시도 없이 terminate 한다.
런타임이 반쯤 맞는 상태로 나온 숫자는 신뢰할 수 없다.

## D-3 — CPU 트랙(운영점 재보정)을 GPU 트랙과 **병렬**로 돌린다

**결정.** GPU 학습을 기다리는 동안 `OPPOINT_RUN_SPEC.md` §8(운영점 확장)을 실행한다. **비용 $0.**

**가설.** 배포 경로(`_detect` greedy)는 **임계값이 암묵적**이다. 임계값을 명시적으로 고르면
같은 모델·같은 가중치에서 precision/recall 균형을 사업 목표 쪽으로 옮길 수 있다.

**근거 (오늘 세 번 같은 곳을 가리켰다).**
| 측정 | 관찰 |
|---|---|
| `SC_INFO_RESULTS.md` | SC 의 이득은 정보량이 아니라 **운영점 이동**이었다 |
| `DOSE_RESULTS.md` §4 | GEN-F1 진동은 적합 실패가 아니라 **판정 경계 이동**이었다 |
| `V3_RESULTS.md` 부록 A | **판별력은 안정, 임계값은 불안정** |

**대안.** GPU 결과를 기다렸다가 v4 로만 운영점을 잡는다 — 기각.
① v4 는 `NO-ADOPT` 가 유력하다(D-0). ② 배포 중인 것은 v1 이므로 v1 의 운영점이 **지금 제품에 대한 답**이다.
③ $0 이고 GPU 와 자원이 겹치지 않는다.

**무엇이 나오면 생각을 바꾸나.**
- 어떤 OP 도 `내부 test recall ≥ 0.75 AND FPR ≤ 0.15` 를 만족하지 못하면
  → "운영점 선택으로도 못 지킨다"가 결과다. 그렇게 적고 배포를 바꾸지 않는다.
- OP-0(현 greedy)이 이미 최선이면 → 배포 변경 없음. 그것도 결과다.

**되돌리는 법.** 배포 반영은 `SCANOPS_TAU` **환경변수**로만 한다.
미설정 시 코드 경로는 현행 greedy 그대로 — 변수를 지우면 즉시 원상복귀다. 어댑터/가중치는 건드리지 않는다.

## D-4 — `PRECISION-UNREACHABLE` 을 어떻게 서술할지 (문구 고정)

**결정.** 아래 문장 형태로만 쓴다. 다른 축약은 쓰지 않는다.

> CleanVul_v2 분포에서 v1 의 AUC(report 0.6165)가 주는 precision 상한이 0.70 아래다.
> tune 에서 사전등록 규칙으로 고른 τ=1.375 를 report 에 1회 적용한 결과
> **precision 0.6465 [95% CI 0.6084–0.6877], recall 0.1419** 였다.

**이 상한을 만든 것은 두 가지이며, 둘 다 적는다.**
1. **벤치가 재는 질문이 다르다.** `FINAL_ARCHITECTURE_REPORT.md` §4 — CleanVul 쌍의 38% 가
   동일 슬라이스이고, 54% 가 비-sanitizer 패치다.
2. **모델의 도메인 밖 판별력이 부족하다.** 내부 test AUC 0.9052 vs 외부 0.5618~0.6165.
   같은 모델이 분포가 바뀌면 거의 무작위에 가까워진다. 이건 벤치 탓으로 넘길 수 없다.

**금지.** "벤치 라벨이 틀렸다"고 쓰지 않는다 — 측정한 것은 라벨이 **다른 질문을 잰다**는 것이지 오류가 아니다.
"수학적으로 증명"이라고 쓰지 않는다 — 잰 것은 한 벤치의 한 분포에서의 상한이다.

**함께 적어야 하는 반대 방향 사실.** `DOSE_RESULTS.md`: 같은 CleanVul 벤치에서
step 450 → 750 학습으로 **AUC +0.019, 부트스트랩 CI 가 0 을 배제**했다.
따라서 **"벤치 때문에 학습이 무의미하다"는 결론은 데이터와 어긋난다.** 이 문장을 빠뜨리지 않는다.

**무엇이 나오면 생각을 바꾸나.** v4 완주 결과가 CleanVul_v2 report AUC 0.75 이상이면
"상한" 서술의 근거(AUC 0.62)가 바뀐다. 그때는 이 절을 통째로 다시 쓴다.
