## 0. 한 줄 결론

> **판단 불가 (INCONCLUSIVE).** graph 단독 전환은 이 실험으로 결정할 수 없다.
> 사전 등록한 중단 게이트 **2개가 동시에 발동**했기 때문이다.

**게이트 1 — unknown 규약 게이트.** 주 규약(unknown=safe)에서 arm(c) recall = **0.0128**,
부 규약(unknown=vuln)에서 **0.9361**. 차이 **0.9233** ≫ 사전 등록 상한 0.10.
사양서가 지정한 대로 결론은 **"graph 단독 전환 판단 불가"로 확정**한다.

**게이트 2 — 판정 회피 게이트.** graph 측정 가능 1,878건 중 **1,721건(91.6%)에서
graph가 `unknown`을 반환**했다. 언어별로도 Java 0.867 / Python 0.946 / JavaScript 0.981로
**세 언어 전부 상한 0.70을 초과** → 세 언어 모두 GO/KILL 판정 대상에서 제외.

**따라서 반드시 이렇게 읽어야 한다:**

> **arm(c)의 낮은 recall(0.013)은 오탐 억제가 아니라 판정 회피에서 온 것이다.**
> graph는 틀린 게 아니라 **10건 중 9건에서 답을 하지 않았다.** 이 구분 없이 KILL을 적으면
> "graph가 탐지를 못한다"는 잘못된 서사가 만들어진다. 실제로 일어난 일은
> **"graph를 탐지기로 쓰는 실험 자체가 성립하지 않았다"** 이다.

참고로 게이트를 걷어내고 사전 등록표를 기계적으로 대입하면 주 규약에서 두 어댑터 모두
전 언어 `KILL`이 나온다(§1). 그러나 그것은 위 이유로 **채택하지 않는다.**

### 부수적으로 확정된 것 (이건 판단 가능하다)

**현행 하이브리드에서 graph를 꺼도 아무 일도 일어나지 않는다.**
arm(a) LLM+graph vs arm(b) LLM만: **ΔF1 = −0.0014, 95% CI [−0.0043, +0.0011] — 0을 포함.**
ΔAUC = −0.0001, CI [−0.0009, +0.0005] — 0을 포함. v3s42도 동일(ΔF1 CI [−0.0059, +0.0009]).
즉 **graph는 지금 하이브리드에 측정 가능한 기여를 하지 않는다.** (§3)

## 6. 판정에 따른 다음 행동 (판단 불가 → 내일 결정용 재료)

### 6-1. 오늘 데이터가 **말할 수 있는** 것

1. **"LLM을 빼고 graph 단독으로 간다"는 지금 상태로는 실행 불가다.** graph는 CleanVul 코드의
   91.6%에서 판정을 거부한다. 탐지기로 세우면 주 규약에서 recall 0.013, 부 규약에서 자명 기준선이 된다.
2. **"graph를 빼도 하이브리드는 그대로다."** (b)−(a) ΔF1·ΔAUC CI가 **두 어댑터 모두 0을 포함**한다.
   현행 결합 규칙(OR)에서 graph의 기여는 **측정 한계 이하**다.
3. **graph의 진짜 문제는 정확도가 아니라 적용률(coverage)이다.** graph=vuln 20건의 precision은 0.60으로
   나쁘지 않다. 문제는 그게 **1,878건 중 20건**이라는 것이다.
4. **모듈별 실패 양상이 다르다.** Java는 `_taint_category()`가 카테고리를 못 잡아 unknown(756/772),
   Python/JS는 sink 목록에 안 걸려 unknown(850/949). **원인이 달라서 해법도 다르다.**

### 6-2. 오늘 데이터가 **말할 수 없는** 것 (내일 이걸 근거로 쓰지 말 것)

- **C/C++에 대해 아무것도 말하지 않는다.** 실서비스 트래픽에서 C/C++ 비중이 크다면 이 실험은 그 부분을
  전혀 다루지 않았다.
- **멀티파일 코드그래프(`code_graph.py`)에 대해 아무것도 말하지 않는다.** 사업계획서에 그 문구가 있다면
  이 실험은 그 근거가 되지 못한다.
- **OWASP Benchmark 성능에 대해 아무것도 말하지 않는다.** `java_graph.py`는 OWASP에서
  재현율 81.8% / F1 83.3을 낸 자산이고(메모리 기록), 여기서 무너진 것은 **CleanVul이라는 다른 분포**에서다.
  둘은 모순이 아니라 **일반화 실패**의 증거다.

### 6-3. 내일 결정을 위해 제안하는 선택지 (권고는 하되 결정은 사용자 몫)

| 안 | 내용 | 비용 | 이 데이터가 지지하는가 |
|---|---|---|---|
| **A. 현상 유지** | 하이브리드 그대로 두고 graph는 보조로 남김 | 0 | ✅ (b)−(a) 차이 없음 = 빼도 되지만 **굳이 뺄 이유도 없다** |

### 8-3. 교집합 비율의 **대체 지표** — 규칙 적용률 (raw만으로 계산 가능한 것)

8-1로 원 지표가 불가능하므로, "graph의 11종 규칙이 해당 코드에 실제로 하나라도 걸렸는가"
(`graph_category != "?"`)를 대신 계산했다.

| 대상 | 규칙 적용됨 | 비율 |
|---|---|---|
| 지원 언어 전체 | 272 / 1,878 | **0.145** |
| **gold=vuln만** | **137 / 939** | **0.146** |
| ├ Java | 63 / 445 | 0.142 |
| ├ Python | 57 / 288 | 0.198 |
| └ JavaScript | 17 / 206 | 0.083 |

**실제 취약 함수의 85.4%에서 graph의 11종 규칙이 아무것도 걸리지 않았다.**
걸린 137건의 계열 내역: **taint 7종 120건 / 원시형 4종 11건 / java 전용(xpathi·trustbound) 6건.**

⚠️ **이 대체 지표는 원 지표를 대신하지 못한다.** 규칙 미적용은
"벤치가 taint 계열이 아니다"와 "graph 규칙이 부실하다"를 **구분하지 못한다.**
두 원인이 정확히 §6의 결론을 가르는 지점이므로, 이 숫자로 §6을 고치지 않았다(8-5).

### 8-5. 사전 지정 트리거 판정 — **미발동. §6을 고치지 않았다.**

| 조건 | 판정 |
|---|---|
| ① taint 계열 CWE 비중 < 30% | **판정 불가** — 지정 데이터(메타 CWE 분포)가 존재하지 않는다(8-1) |
| ② unknown 사유의 **과반**이 "source 미발견" | **불성립** — 실측 **6.3%**. 과반은 sink 미발견(49.4%)과 카테고리 미결정(43.9%)이다(8-4) |

**따라서 지정된 문장을 §6에 추가하지 않았다.** 두 조건 모두 성립하지 않았고,
성립하지 않은 트리거로 결론 문장을 넣으면 이 리포트 전체가 지킨 사전 등록 규율이 깨진다.

**다만 실측은 같은 방향을 가리킨다 — 단, 다른 메커니즘으로.**
트리거 ②는 "패턴은 맞는데 흐름 추적에 실패한다"(= graph **성능** 문제)를 겨냥해 쓰였는데,
실제로 관찰된 것은 **"패턴 자체가 없다"**(= **적용 범위** 문제)다. 이건 트리거가 상정한 것보다
범위 불일치 쪽으로 **더 강한** 증거다. 그러나 8-3의 경고대로 raw만으로는
"벤치가 taint 계열이 아니다"와 "graph 규칙이 부실하다"를 분리할 수 없으므로,
문장을 채택하려면 **CWE 라벨이 있는 벤치에서 조건 ①을 실제로 재는 절차가 선행**되어야 한다.
그 절차를 새 사양서에 등록하기 전까지 §6은 그대로 둔다.

### 8-6. 조건 ① 선행 절차 실측 — (A) 벤치 불일치 채택, (B) 규칙 부족 기각

§8-5가 요구한 선행 절차를 수행했다. CPU 후처리 + `multi_graph.analyze()` 호출만,
LLM 추론·GPU 없음, 기존 파일 무수정.
스크립트: `rebuild/ablation_coverage_bench.py` /
산출물: `out/ablation_coverage_bench.json`, `out/ablation_coverage_raw_{cvefixes,owasp}.jsonl`

**사전 등록 판정 규칙 (사후 변경 없음)**
- OWASP에서 graph unknown 비율 > 0.50 → **(B) 규칙 부족** 채택
- CVEfixes taint 계열 CWE 비중 < 0.30 → **(A) 벤치 불일치** 채택
- 둘 다 성립하면 둘 다 적는다(배타적이지 않다)
- OWASP 결과는 `multi_graph.py`/`java_graph.py`가 OWASP 형태를 알고 설계된
  자산이므로(V11 과적합 경고, 두 파일 docstring) **(B)의 반증 용도로만** 쓰고
  graph 성능 근거로는 인용하지 않는다

| 가설 | 조건 | 실측 | 판정 |

**(A)만 채택한다.** 같은 graph, 같은 unknown 분류 기준으로:

| 벤치 | 성질 | graph unknown 비율 | 지배 사유 |
|---|---|---|---|
| OWASP holdout | 합성, taint 중심 설계 | **0.264** | 흐름 미해결(source는 **있음**) |
| CleanVul_v2 (지원 언어) | 실제 CVE 수정, 함수 단위 | 0.916 | sink 미발견 + 카테고리 미결정 |
| CVEfixes | 실제 CVE 수정, 함수 단위 | **0.981** | sink 미발견 + 카테고리 미결정 |

unknown 비율은 graph가 아니라 **벤치를 따라간다.** 실제 CVE 계열 벤치에서 taint 7종
CWE는 vuln의 8.75%뿐이고, graph의 판정 회피는 "흐름 추적 실패"가 아니라
"아는 패턴이 코드에 없음"에서 나온다. 이로써 §8-5가 유보했던 문장을 **채택한다**:

> **"이 실험은 graph의 성능이 아니라 벤치와 graph의 적용 범위 불일치를 측정했다.
> CleanVul/PrimeVul 계열 함수 단위 벤치로는 taint 그래프를 평가할 수 없다."**

(§0~§7은 사전 등록 규율 유지를 위해 수정하지 않고, 채택 사실을 이 부록에만 기록한다.
내일 리팩토링 결정 시 §6-3의 선택지 표와 이 §8-6을 함께 읽을 것.)

`java_graph.py`는 OWASP 형태(서블릿·doSomething 헬퍼·bar 변수)를 알고 설계된 자산이다

(B)를 완전히 기각하려면 graph 설계와 독립인 taint 중심 벤치가 필요하다 — 현재 없다.
