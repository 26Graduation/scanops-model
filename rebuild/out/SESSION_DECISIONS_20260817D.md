- **어떤 스캔 결과도 보기 전에 커밋**했다(`72d18e0`). 스캔은 그 이후 커밋에 있다 — 순서로 확인 가능.
- 보수적으로 뺀 것을 파일에 명시했다(`_not_marked`): login.ts:34, search.ts:23,
  updateProductReviews.ts, app.routing.ts 186/239/261/300, search-result.component.ts:144, .sol 3건.

**바꿀 조건.** 제3자가 특정 건의 cross_file 판단을 반박하면 그 건을 빼고 재계산한다.

## D-35. 매칭 단위를 **파일**로 바꿨다 (측정 전) — 21:20

**문제.** 사양 §6-d 는 `sink_line ±10 또는 같은 함수` 였다. 그런데
**우리 모델도 Claude 도 라인 번호를 출력하지 않는다** — 4줄 서식(VULNERABILITY/SEVERITY/CVSS/REASON)에
라인이 없고, 제품 `/analyze/batch` 도 파일 단위 판정만 낸다.

**대안**
1. 라인 기준 유지 → LLM arm 두 개가 구조적으로 0. 비교가 성립하지 않는다
2. **세 arm 전부 파일 단위** ← 선택
3. LLM 에 라인을 내라고 프롬프트를 바꾼다 → **PARITY 가 깨진다**(프롬프트 바이트 동일 조건)

**이유.** (2)만 세 arm 에 동일하게 적용되고 제품 동작과도 일치한다.
**대가**: recall 이 낙관적이 된다(파일 어딘가에 취약이 있으면 맞은 것으로 센다).
**세 arm 에 똑같이 낙관적**이고, 표 각주에 적었다. 사양 §11 S-1 에 기록.

**바꿀 조건.** 라인 번호를 내는 출력 서식으로 제품을 바꾸면 라인 기준으로 되돌린다.

## D-36. Claude PARITY 를 `thinking: disabled` 로 돌린다 — 21:30

**문제.** `temperature=0` 을 Claude 5 계열에 줄 수 없다(sampling 파라미터 400).
"동일 조건"을 만들 수 없다.

**대안**
1. 기본값(adaptive thinking)으로 돌린다 → 우리 단일 패스와 조건이 크게 다르고 비용이 4~6배
2. **`thinking: disabled` + max_tokens 400** ← PARITY 로 선택
3. 조건을 못 맞추니 비교를 포기한다

**이유.** (2)가 우리 greedy 단일 패스에 가장 가깝다. **그리고 (1)에 해당하는 조건을
STRONG arm 으로 따로 준다** — "불리한 프롬프트를 줬다"는 반박을 막기 위해서다.
**맞출 수 없는 조건(temp 0)은 표 각주에 그대로 적는다.**

**바꿀 조건.** STRONG 이 PARITY 보다 크게 높으면, 대외 인용은 **STRONG 쪽**을 쓴다.

## D-37. `[DIFF]` 마커를 **기본 on** 으로 제품에 붙였다 — 22:10

**대안**

2. **플래그로 붙이고 기본 on** ← 선택

**이유.** 게이트를 막은 것은 **동점률 하나**이고, 나머지는 전부 우호적이다:

CyberNative +0.0176), 안전 판본 오탐률 **0.065 불변**.
**게이트 통과가 아니라 제품 판단**이라고 문서에 적었고, 되돌림은 환경변수 하나다.
구현은 `prompt_code` 를 따로 두어 **graph/Joern/점수 경로는 원본 코드**를 보게 했다.

**바꿀 조건.** 운영에서 PR 오탐이 늘면 `SCANOPS_PR_DIFF_MARKER=0`. 회귀 4종은
