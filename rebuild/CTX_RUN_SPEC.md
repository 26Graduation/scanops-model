# CTX-1 실행 사양서 — "문맥 주입이 판별력을 살리는가" 하루짜리 검증

작성 기준: `rebuild/out/V3_RESULTS.md` (2026-08-14 04:57 종료분)
선행 근거: V3 §3-3(도메인 데이터 32% 투입 → PrimeVul AUC 0.562 → 0.580), §10 우선순위 1
예산: **6시간 / $6 이하** · 재학습 **금지**

---

## 0. 이 실행의 목적 (한 줄)

**v1 어댑터를 그대로 두고 입력 표현만 바꿨을 때 외부 벤치 판별력(AUC)이 오르는지**를,
Joern·taint 엔진을 한 줄도 만들기 전에 판정한다.

이 실험은 성능 개선이 목적이 아니다. **하이브리드 피벗(SAST 탐지 + LLM Critic)에
2~3주를 투자할지 말지를 결정하는 GO/KILL 게이트**다. 결과가 나쁘면 그게 성공한 실행이다.

---

## 1. 가설과 반증 조건

- **H1 (베팅)**: v1의 외부 AUC 0.56~0.62는 모델 능력 한계가 아니라 **함수 단위 입력의 정보 부족** 때문이다.
  문맥을 주면 오른다.
- **H0 (귀무)**: 문맥을 줘도 안 오른다. 즉 LLM Critic 단계 자체가 성립하지 않는다.

H0가 살아남으면 **피벗 3단계 구조를 축소해야 한다** — LLM은 검증(2단계)에서 빼고
수정 제안(3단계) 전용으로 내린다. 그 판단도 이 실행의 정당한 산출물이다.

---

## 2. 실험 팔 (arm) — 반드시 4개 다 돌린다

모두 **동일한 v1 어댑터**(`out/adapter/`, 무수정)로, **동일한 케이스 집합**에서 측정한다.

| arm | 프롬프트 입력 | 목적 |
|---|---|---|
| **T0** | 현행 함수 단위 (기존과 완전 동일) | 기준선 재현 — 파이프라인 정상 동작 확인 |
| **T1** | 함수 + **그 함수가 속한 파일의 문맥** (아래 §3) | 본 실험 |
| **T1-shuf** | 함수 + **무작위 다른 파일**에서 뽑은 같은 분량의 문맥 | **길이/형식 교란 통제** |
| **T1-nofunc** | 문맥만, 대상 함수 본문 제거 | 정보가 문맥 쪽에 있는지 역검증 (싸니까 같이) |

> **T1-shuf가 이 실험의 핵심이다.** 프롬프트가 길어지기만 해도 logprob 분포는 움직인다.
> T1이 올랐는데 T1-shuf도 같이 올랐다면 그건 정보 효과가 아니라 아티팩트다. 빼먹지 마라.

## 3. 문맥 추출 (T1) — 레포 클론 금지, 파일 1개만 받는다

대상: **PrimeVul report split** (`split_tune_report.py`가 만든 report 쪽, 144쌍 / 288건).
CleanVul_v2는 시간 남을 때만.

1. `data/raw/primevul_test_paired.jsonl`을 먼저 **읽고 실제 필드명을 확인**한다.
   (`project` / `commit_id` / `file_name` / `func` / `project_url` / `commit_url` 계열이 있을 것으로 기대하되,
   없으면 있는 것으로 대체하고 그 사실을 리포트에 적는다.)
2. GitHub raw API로 **해당 커밋 시점의 그 파일 1개만** 받는다. 클론하지 않는다.
   `GITHUB_TOKEN` 사용, 결과는 `rebuild/data/ctx_cache/`에 캐시(재실행 무료).
3. 파일에서 대상 함수를 찾고, 다음을 조립한다:
   - 파일 상단의 `#include` / import / 매크로 / 상수 정의
   - 대상 함수가 참조하는 **구조체·타입 정의** (같은 파일 내)
   - **같은 파일 안에서 대상 함수를 호출하는 지점** ±20줄
   - 대상 함수가 호출하는 **같은 파일 내 함수 본문**
   - 대상 함수 본문 (원문 그대로)
4. **상한 8,000 토큰**. 초과 시 위 우선순위 역순으로 잘라내고, **잘린 비율을 케이스별로 기록**한다.
5. 취약/패치 두 버전 모두 **각자의 커밋에서** 문맥을 받는다. 한쪽 문맥을 양쪽에 쓰면 실험이 무효다.

### 절대 넣지 말 것 (라벨 누출)

- 패치 diff, 커밋 메시지, CVE ID, CWE ID, `target` 필드
- 커밋 날짜, 브랜치명, 파일명 중 `fix`/`patch`/`vuln` 류 문자열
- 두 버전 간 차이를 드러내는 어떤 메타데이터도 금지

**작업 시작 전에 `check_repo_leakage_and_keywords.py`를 문맥 텍스트에 대해 돌려서 누출을 기계적으로 확인한다.**

## 4. 측정 규칙 (V3 무결성 규칙 승계 — 위반 시 결과 폐기)

1. **평가 3종 파일 수정 금지.** 읽기만. `bench_common.py` 파서·지표 손대지 않는다.
2. **주 지표는 AUC와 pair_rank_correct.** F1은 부가 정보로만 병기한다.
   - `pair_rank_correct = mean[ score(vuln) > score(patched) ]`, **우연 기준선 정확히 0.500**
   - 모든 표에 **자명 기준선(무조건 VULNERABLE → F1 0.667)을 같은 표 안에** 적는다
3. **점수는 logprob 방식으로 낸다.** `score_logprob.py`의 `PREFIX="VULNERABILITY:"` 로직 그대로.
   `score = logP(' CWE') - logP(' NONE')`. 케이스당 0.18초, 생성 대비 6배 저렴.
4. **어시스턴트 응답 포맷을 바꾸지 마라.** 문맥은 **user 메시지에만** 추가한다.
   첫 줄이 `VULNERABILITY:`가 아니게 되는 순간 logprob 층 전체가 무효가 된다.
5. **arm 간 비교는 반드시 동일 케이스 부분집합에서 한다.**
   문맥 수집에 실패한 케이스는 **모든 arm에서 함께 제외**한다.
   (V3 §2-3에서 Claude를 다른 데이터로 비교해 결론이 무너졌던 실수의 재발 방지)
6. 수집 성공률과, **성공 부분집합에서의 T0 AUC vs 전체 288건 T0 AUC**를 병기한다.
   둘이 0.05 이상 벌어지면 표본 편향을 리포트 맨 위에 경고로 적는다.
7. 임계값이 필요한 지표는 **tune split에서만** τ를 고른다. report split에서 고르면 폐기.
8. **ΔAUC는 부트스트랩 2,000회 신뢰구간과 함께 보고한다.** `bootstrap_ci.py` 재사용.
9. 최소 표본: **100쌍 이상 권장, 60쌍 미만이면 판정하지 말고 "검정력 부족"으로 보고.**

## 5. 사전 등록 판정표 — 실행 전에 확정, 사후 변경 금지

기준은 **PrimeVul report split의 T1 AUC** 및 **ΔAUC = T1 − T0**.

| 판정 | 조건 | 다음 행동 |
|---|---|---|
| **GO** | T1 AUC ≥ 0.68 **AND** ΔAUC 95% CI 하한 > 0 **AND** T1 − T1-shuf ≥ 0.05 | Joern CPG 슬라이스(T2)로 진행. 하이브리드 피벗 확정 |
| **WEAK** | 0.62 ≤ T1 AUC < 0.68 이고 CI 하한 > 0 | 문맥이 방향은 맞음. **T2(호출부 교차파일)까지만** 추가 검증 후 재판정 |
| **FORMAT-SHOCK** | T1 ≈ T1-shuf 이고 **둘 다 T0보다 낮음** | 문맥 무용이 아니라 **v1이 긴 입력을 못 먹는 것**. 결론은 "문맥 포맷으로 재학습 필요"이며 KILL이 아니다 |
| **ARTIFACT** | T1 상승분과 T1-shuf 상승분의 차이 < 0.05 | 상승은 길이 효과. **GO 아님.** 실패로 기록 |
| **KILL** | T1 AUC < 0.62 **또는** ΔAUC CI가 0을 포함 (그리고 shuf 통제 통과) | **LLM Critic 단계를 접는다.** SAST 단독 탐지 + LLM 수정 제안 전용 구조로 축소 |

FORMAT-SHOCK과 KILL을 구분하는 것이 이 판정표의 존재 이유다. 뭉뚱그리지 마라.
